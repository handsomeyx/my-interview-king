# TCP 与 HTTP 深入（可靠性 / 拥塞控制 / 缓存 / 粘包）

> 配套：[网络总览](./) 已讲分层 + 三次握手 + HTTPS。本篇深入 TCP 怎么保证可靠、HTTP 缓存怎么命中、粘包从哪来。

---

## Q1：TCP 怎么保证可靠传输？

**答**：四件大事：
1. **校验和**：每段加校验和，接收方验证，错了丢弃（等重传）。
2. **序列号 + 确认号**：每个字节有序号，接收方回 ACK（确认号 = 期望收到的下一个序号）。丢了能发现 + 重排。
3. **重传**：发送后启动定时器，超时未收到 ACK 就重传（超时重传）；或收到 3 个重复 ACK 触发快重传。
4. **流量控制**：滑动窗口（接收方告诉发送方「我能收多少」），防发太快接收方缓冲溢出。

**易错点**：序列号是「**字节**」的序号，不是「段」的序号。一个段带「序号 = 上次发完的 +1，长度 N」，下一段序号 = 这个 + N。确认号是「**期望下一个收到的**序号」。

## Q2：滑动窗口 vs 拥塞窗口？

**答**：
- **滑动窗口（rwnd）**：**接收方**的流量控制。接收方在 ACK 里带 window size，告诉发送方「我缓冲还剩多少」，发送方不超发。
- **拥塞窗口（cwnd）**：**发送方**的拥塞控制。发送方自己维护，根据网络拥塞程度动态调（慢启动 / 拥塞避免）。cwnd 在网络拥塞（丢包）时减半。
- **实际发送窗口 = min(rwnd, cwnd)**：接收方能力和网络能力取小。

**易错点**：滑动窗口是「**接收方限速**」（防接收方溢出），拥塞窗口是「**网络限速**」（防网络拥塞）。两者独立，实际发送取 min。新人常混。

## Q3：TCP 拥塞控制四算法？

**答**：
1. **慢启动**（slow start）：连接初期 cwnd 从 1 **指数增长**（每 RTT 翻倍），快速探测带宽。到 ssthresh（慢启动阈值）转拥塞避免。
2. **拥塞避免**：cwnd 超过 ssthresh 后**线性增长**（每 RTT +1），谨慎探测。
3. **快重传**（fast retransmit）：收到 **3 个重复 ACK**（不等超时），立即重传丢失段。
4. **快恢复**（fast recovery）：快重传后不回慢启动，而是 cwnd 减半 + ssthresh = cwnd/2，继续拥塞避免（不是从 1 开始）。

**超时 vs 快重传**（关键区别）：
- **超时**（定时器到）：网络严重拥塞 → cwnd = 1，ssthresh = cwnd/2，重新慢启动。
- **快重传**（3 重复 ACK）：轻度拥塞（段能到、ACK 能回，只是丢个别段）→ cwnd 减半，不回 1。

**易错点**：「慢启动」**不慢**（指数增长），名字误导。它叫「慢启动」是因为「**起点小**（cwnd=1）」，不是增长慢。

## Q4：HTTP 缓存机制？

**答**：两级：
- **强缓存**（不发请求，直接用本地）：`Cache-Control: max-age=N`（N 秒内直接用缓存）或老版本的 `Expires`（绝对时间）。浏览器显示 `from disk/memory cache`。
- **协商缓存**（发请求问服务器「变了没」）：
  - `Last-Modified` / `If-Modified-Since`（精度秒）：服务器对比文件修改时间，没变返 304，变了返 200 + 新内容。
  - `ETag` / `If-None-Match`（哈希，精度更高）：服务器对比 ETag，没变 304。

**优先级**：Cache-Control > Expires；ETag > Last-Modified。命中强缓存就不发请求；强缓存过期才走协商缓存。

**易错点**：`no-cache` **不是「不缓存」**——是「每次用前要问服务器（协商缓存）」。`no-store` 才是「完全不缓存」。新人常把 no-cache 当 no-store。

## Q5：TCP 粘包怎么解决？

**答**：TCP 是**字节流**（无边界），应用层消息边界要自己定。粘包/半包根因就是「TCP 不维护消息边界」。三种解法：
1. **定长消息**：每条固定长度（不够补齐）。简单但浪费。
2. **分隔符**：消息间加特殊字符（如 `\n`），HTTP 的 `\r\n`、Redis RESP 协议都是。
3. **长度前缀**（最常用）：消息头带「长度 N」，接收方按 N 读。Netty 的 `LengthFieldBasedFrameDecoder` 就是这个。

**易错点**：「TCP 粘包」名字误导——TCP **没错**（它就是流式协议），是**应用层没定边界**。UDP 不粘包（每个数据报独立）。所以「粘包」是应用层问题，不是 TCP bug。

## 易错点速查表

| 知识点 | 关键 |
|---|---|
| 序列号 | 字节的序号（不是段的）；确认号 = 期望下一序号 |
| 滑动窗口 rwnd | 接收方限速（流量控制） |
| 拥塞窗口 cwnd | 发送方限速（拥塞控制） |
| 实际发送窗口 | min(rwnd, cwnd) |
| 慢启动 | 指数增长，名字误导（起点小不是增长慢） |
| 超时 vs 快重传 | 超时回 cwnd=1；快重传减半不回 1 |
| no-cache | 协商缓存（问服务器），不是不缓存；no-store 才不缓存 |
| 粘包 | TCP 是流无边界，应用层定边界（长度前缀最常用） |
