# 垃圾收集深入（三色标记 / G1 / ZGC / 调参）

> 配套：[JVM 总览](./) Q3/Q4 已讲 GC 算法 + 收集器概览。本篇深入：**并发标记怎么不漏标（三色）、跨代引用怎么处理（卡表）、G1 和 ZGC 的核心机制、生产 GC 调参**。

---

## 思考锚点

Java 程序运行时，对象不断被创建，如果不清理不再使用的对象，内存很快就会耗尽。但「清理没用的对象」说起来简单，实现起来有两个核心难题：怎么判断对象「没用了」？清理时怎么不让用户线程卡住太久？

GC 的演化史就是在这两个问题上不断权衡的过程：从 Serial 的单线程 stop-the-world，到 CMS 的并发标记+清除，到 G1 的可预测停顿，再到 ZGC 的亚毫秒级停顿。

本文要讲清楚各种 GC 的核心机制、它们之间的对比，以及生产中怎么选型和调优。

## Q1：三色标记与漏标

**答**：并发标记（GC 线程和用户线程同时跑）用**三色标记**：
- **白**：未访问（GC 结束还是白 = 垃圾）。
- **灰**：已访问，但它的引用字段还没扫完。
- **黑**：已访问且引用字段都扫完（存活，不会再扫）。

**漏标问题**：并发标记时，用户线程改了引用，可能让「存活对象」被误判为白：
1. 把黑对象到白对象的引用删了（白失去唯一灰色引用路径）。
2. 灰对象新建一条到白对象的引用，但灰→黑的推进没扫到。

结果：白对象被当垃圾回收 → **漏标，存活对象丢了**。

**解决**：用**写屏障**（write barrier）在引用变更时通知 GC：
- **CMS（增量更新）**：黑对象新增引用时，记录这个黑对象，重新标记阶段把它当灰的再扫一遍（只重扫新增的）。
- **G1 / SATB（Snapshot At The Beginning）**：引用要被删除时，记录**原来的引用**（在并发标记开始时拍快照），结束阶段处理这些引用。SATB 保证了「标记开始时的存活对象」一定能被标到。

**易错点**：CMS 用增量更新，G1 用 SATB——两者都解决漏标，但机制不同。SATB 在并发标记开始拍快照，可能标到「标记过程中变垃圾」的对象（浮动垃圾，下轮回收）；增量更新更精确但重扫成本高。

## Q2：跨代引用怎么处理？

**答**：分代 GC 假说「跨代引用少」。但老年代引用新生代（或反之）确实存在。GC 新生代时不能扫整个老年代找谁引用了新生代（成本太高），所以用**记忆集**（Remembered Set）：

- **卡表**（Card Table）：把老年代分成固定大小的「卡」（512B），用一个字节数组标记每张卡「是否引用了新生代」。新生代 GC 时只扫「脏卡」对应的老年代区域，不全扫。
- **写屏障维护**：对象引用变更时，如果老年代对象引用了新生代，写屏障把对应卡标脏。

**易错点**：写屏障不是「锁」，是「GC 的记账操作」（标记卡脏）。它有性能开销（每次引用写都触发），这是 G1 写屏障优化的重点（减少精度换性能，或反之）。

## Q3：G1 的核心机制？

**答**：G1（Garbage First）和传统分代 GC 的关键区别：

1. **Region 化堆**：堆被切成 2048 个左右的 Region（1-32MB 每个），每个 Region 动态扮演 Eden / Survivor / Old / Humongous（大对象），不是物理固定的新生代/老年代。
2. **全局标记 + 回收价值**：G1 先全局标记哪些 Region 垃圾最多，然后**优先回收价值最高（垃圾最多）的 Region**——「Garbage First」得名。所以叫「垃圾优先」。
3. **可预测停顿**：`-XX:MaxGCPauseMillis=200`（默认 200ms），G1 根据历史数据估算「在 200ms 内能回收多少 Region」，只回收能完成的，不超时。
4. **Mixed GC**：G1 不分 Full GC / Minor GC，用 Mixed GC（同时回收年轻代 Region + 部分老年代 Region），避免 Full GC 长停顿。
5. **SATB + Remembered Set**：Region 间引用用 Remembered Set 维护，避免全堆扫。

**易错点**：G1 的「可预测停顿」是**尽力**，不是保证。如果 Region 里存活对象太多（搬移成本高），单次仍可能超 MaxGCPauseMillis。所以生产调参别设太小（如 50ms），否则 G1 会频繁 GC 反而吞吐下降。

## Q4：ZGC 为什么停顿 <10ms？

**答**：ZGC（Z Garbage Collector，JDK 11 实验，15 产品，16 去 experimental）的核心：

1. **染色指针**（Colored Pointer）：64 位指针的高 4 位标记对象状态（Marked0/Marked1/Remapped/Finalizable）。GC 通过改指针颜色标记对象，不用改对象头。
2. **读屏障**（Load Barrier）：对象引用被读时，读屏障检查指针颜色，如果颜色不对（对象被搬移过），**就地修复指针**（转发到新地址）。这避免了搬移时全堆更新引用——延迟到下次读时修。
3. **并发搬移**：标记、搬移都和用户线程并发（STW 只在初始标记 / 重新标记的极短阶段）。搬移用染色指针 + 读屏障，用户线程读时修指针。

**代价**：吞吐量下降（读屏障开销，约 10%），换极低停顿。适合「停顿敏感」场景（金融交易、低延迟服务）。

**易错点**：ZGC 的读屏障是**每读都触发**（Load Barrier），不是写屏障。这是它「并发搬移不漏」的关键——但读屏障比写屏障触发更频繁，吞吐开销大。所以 ZGC 牺牲吞吐换停顿，吞吐优先场景用 G1/Parallel。

## Q5：生产 GC 怎么调参？

**答**：
- **选收集器**：JDK 8 默认 Parallel（吞吐）；JDK 9+ 默认 G1（平衡）；低延迟用 ZGC（`-XX:+UseZGC`）。
- **G1 关键参数**：
  - `-XX:MaxGCPauseMillis=200`（停顿目标，别设太小）。
  - `-XX:G1HeapRegionSize`（Region 大小，一般自动，大对象多时手调）。
  - `-Xms == -Xmx`（避免扩容抖动）。
- **观察工具**：
  - `jstat -gcutil <pid> 1000`：每秒看 GC 频次 + 各区占用。
  - `-Xlog:gc*`（JDK 9+）或 `-XX:+PrintGCDetails`（JDK 8）：GC 日志。
  - GC 日志上传 [GCEasy](https://gceasy.io)：可视化分析停顿 / 吞吐 / 频次。
- **调优信号**：
  - Full GC 频繁 → 老年代不够（调大堆 / 查内存泄漏）。
  - Minor GC 频繁 → 新生代不够（调大 -Xmn 或 NewRatio）。
  - 停顿长 → 换 G1/ZGC 或调 MaxGCPauseMillis。

**易错点**：调参前先**测基线**（jstat + GC 日志看当前频次/停顿），不要凭感觉加参数。绝大多数应用用默认 G1 就够，乱调反而更差。「先量化，再优化」。

## 易错点速查表

| 知识点 | 关键 |
|---|---|
| 三色标记 | 白/灰/黑；漏标 = 存活被当垃圾 |
| CMS vs G1 并发标记 | CMS 增量更新；G1 SATB（快照 + 浮动垃圾） |
| 卡表 | 老年代引用新生代的记账；写屏障维护 |
| G1 核心 | Region 化 + 优先回收价值最高的 + Mixed GC |
| MaxGCPauseMillis | 尽力而非保证；设太小反吞吐下降 |
| ZGC | 染色指针 + 读屏障；<10ms 但吞吐开销约 10% |
| 读屏障 vs 写屏障 | ZGC 用读屏障（频繁，吞吐开销）；G1 用写屏障 |
| 调参 | 先量化基线，默认 G1 够用，别乱调 |
