# Spring 循环依赖与三级缓存

> Spring 最经典的面试题。很多人能背"三级缓存解决循环依赖"，但追问"三级缓存各自存什么""为什么构造方法循环依赖解决不了"就卡壳。本文把这套机制讲透。

## 思考锚点

Spring 容器启动时，会根据配置创建所有 Bean。但有时候两个 Bean 互相依赖对方才能创建——A 需要 B，B 需要 A，形成死循环。这就是循环依赖。

Spring 用「三级缓存」解决单例 Bean 的循环依赖，核心思路是「提前暴露半成品」：A 还没创建完，就先把它的引用暴露给 B 使用，等 A 创建完了再把成品给 B 换上。但这个方案对构造器注入和 prototype 作用域无能为力。

本文要讲清楚三级缓存的每一级存什么、为什么需要三级（两级不够吗）、为什么构造器循环依赖解决不了，以及 SpringBoot 2.6+ 为什么默认禁止循环依赖。

## Q1：什么是循环依赖？

**答**：两个或多个 Bean 互相持有对方。最常见：A 的字段注入 B，B 的字段注入 A。

```java
@Service
public class A {
    @Autowired private B b;   // A 依赖 B
}
@Service
public class B {
    @Autowired private A a;   // B 依赖 A
}
```

**问题**：创建 A 需要 B，创建 B 又需要 A，死循环。

## Q2：Spring 怎么解决（三级缓存）？

**答**：Spring 用**三级缓存**（`DefaultSingletonBeanRegistry` 的三个 Map）解决**单例 + setter/字段注入**的循环依赖。

| 缓存 | 名字 | 存什么 |
|---|---|---|
| 一级 | `singletonObjects` | **完全初始化**的 Bean（成品） |
| 二级 | `earlySingletonObjects` | **早期暴露**的半成品 Bean（已实例化、未注入完） |
| 三级 | `singletonFactories` | **对象工厂**（lambda，调用它产出早期引用，可能触发 AOP 代理） |

**流程**（A 注入 B，B 注入 A）：
1. 创建 A：实例化 A（构造方法完成），把"A 的对象工厂"放进**三级缓存**。
2. A 开始属性注入，发现需要 B，去创建 B。
3. 创建 B：实例化 B，B 属性注入发现需要 A。
4. B 找 A：从三级缓存拿到 A 的工厂，**调用工厂拿到 A 的早期引用**（此时 A 还没注入完，是半成品），放入二级缓存，删三级缓存的 A。B 拿到 A 的早期引用，B 完成注入，B 成品进一级缓存。
5. 回到 A：A 拿到成品的 B，A 完成注入，A 成品进一级缓存。

**关键**：循环依赖能解，靠的是**"提前暴露半成品"**——A 还没造完，就先把它（的工厂）暴露出去，让 B 先用着。

## Q3：为什么要三级？两级不够吗？

**答**：为了正确处理 **AOP 代理**。

- 如果只有两级（成品 + 半成品对象）：循环依赖里 B 注入的 A 是**原始对象**，但 A 最终可能要被 AOP 包装成**代理对象**。这样 B 拿到原始 A，容器里最终的是代理 A——**两个 A 不一致，AOP 失效**。
- 三级缓存存的是**对象工厂**（不是对象本身）。当 B 来要 A 时，工厂被调用，**此时才决定返回原始 A 还是代理 A**（如果 A 配了 AOP，工厂返回代理）。这样 B 一开始就拿到正确的代理 A，后续一致。

**易错点**：三级缓存不是"为了快"或"多余设计"——它存在的唯一理由是**延迟 AOP 代理的创建时机**，保证循环依赖里注入的对象和最终容器里的对象是同一个（带代理的正确版本）。

## Q4：为什么构造方法循环依赖解决不了？

**答**：构造方法注入要求**实例化时就拿到依赖**。A 的构造方法需要 B，B 的构造方法需要 A——两个对象都还没 `new` 出来，没法"提前暴露半成品"（半成品至少得先实例化）。

三级缓存的"提前暴露"前提是**对象已经实例化**（构造方法已跑完）。构造方法循环依赖卡在**实例化之前**，所以无解。

**报错**：`BeanCurrentlyInCreationException`。

**解法**：把其中一端改成 setter/字段注入，或用 `@Lazy`（注入代理，延迟真实创建）。

**易错点**：记住 **"Spring 只能解决 setter/字段注入的单例循环依赖"**。构造方法注入、prototype 作用域的循环依赖都解决不了。这是面试筛人点。

## Q5：@Lazy 怎么破解循环依赖？

**答**：`@Lazy` 注入的是**代理对象**，不是真实 Bean。第一次真正调用方法时才从容器拿真实 Bean。

```java
@Service
public class A {
    @Autowired @Lazy private B b;   // 注入 B 的代理，不是 B 本身
}
```

这样 A 创建时不需要立刻有真实的 B，打破了"创建时就要依赖"的死结。常用来解构造方法循环依赖。

## Q6：SpringBoot 2.6+ 默认禁止循环依赖？

**答**：是的。`spring.main.allow-circular-references` 默认从 `true` 改成 `false`。启动检测到循环依赖直接报错。

**为什么**：Spring 官方认为循环依赖是**设计坏味道**——说明职责没拆清楚。默认禁止倒逼开发者重构（拆出第三层、用事件解耦、改单向依赖）。

**易错点**：面试问"循环依赖好不好"，别只答"Spring 能解决"。**正确答法**：Spring 能解 setter 单例循环依赖，但循环依赖本身是设计缺陷，SpringBoot 2.6+ 默认禁止，推荐重构而不是依赖三级缓存兜底。这个答案比"三级缓存背一遍"显深度。

## 易错点速查表

| 知识点 | 关键 |
|---|---|
| 三级缓存 | 一级成品 / 二级半成品对象 / 三级对象工厂（工厂存在仅为 AOP 代理）|
| 提前暴露 | 前提是对象已实例化；构造方法循环依赖卡在实例化前，无解 |
| 构造方法循环依赖 | 报 `BeanCurrentlyInCreationException`；解法 `@Lazy` 或改 setter |
| prototype 循环依赖 | 也解决不了（每次新建，无法缓存） |
| @Lazy | 注入代理延迟创建，破解构造循环 |
| SpringBoot 2.6+ | 默认禁止循环依赖（`allow-circular-references=false`） |
| 面试正解 | 循环依赖是设计缺陷，能解但不应依赖 |
