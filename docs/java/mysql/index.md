# MySQL

MySQL 是后端最常用的关系型数据库。面试官爱问的不是“MySQL 是什么”，而是**InnoDB 的索引为什么是 B+ 树、事务隔离级别怎么选、MVCC 怎么实现、锁加在哪、redo/undo/binlog 各干什么**。这篇是总览，每个主题点到面试官追问的深度，细节在子页。

## 存储引擎：InnoDB vs MyISAM

| 维度 | InnoDB（默认） | MyISAM |
|------|---------------|--------|
| 事务 | 支持 | 不支持 |
| 锁粒度 | 行锁（默认） | 表锁 |
| 外键 | 支持 | 不支持 |
| 崩溃恢复 | 支持（redo log） | 不支持 |
| 适用 | 核心业务（订单、用户） | 只读 / 非核心（已少用） |

易错点：InnoDB 的行锁**不是绝对行锁**——走索引命中行才是行锁，**不走索引或索引失效会升级为表锁**。这是“为什么慢 SQL 会锁全表”的根。

## 索引：为什么是 B+ 树

- **B+ 树**：所有数据只在叶子节点（非叶子只存索引），叶子间用双向链表串起来。
  - 为什么不用 B 树：B+ 树非叶子不存数据 → 单节点能塞更多索引 → 树更矮 → 磁盘 IO 更少。
  - 为什么不用 hash：hash 等值快但**范围查询要全扫**，B+ 树叶子链表天然支持范围。
  - 为什么不用红黑树：层数太深（千万级数据要二十多层），磁盘 IO 多；B+ 树 3~4 层就能存千万级。
- **聚簇索引 vs 二级索引**：聚簇索引（主键）叶子存**整行数据**；二级索引叶子只存**主键值**，查二级索引要**回表**（再查一次聚簇索引）。
  - 易错点：**覆盖索引**（查询字段都在二级索引里）不用回表，是优化利器。

索引细节（最左匹配、索引失效、explain 调优）见 [索引原理](/java/mysql/indexing)。

## 事务：ACID 与隔离级别

- **ACID**：原子（undo log）、一致（业务约束）、隔离（锁 + MVCC）、持久（redo log）。
- **四个隔离级别**（隔离性从低到高）：
  1. 读未提交（RU）：脏读。
  2. 读已提交（RC）：不可重复读。Oracle 默认。
  3. 可重复读（RR）：标准说还有幻读。**MySQL 默认**。
  4. 串行化（Serializable）：锁表，性能差。
- 易错点：MySQL 的 RR **用 MVCC + 间隙锁额外解决了幻读**（不像标准 SQL 的 RR 仍有幻读）。这是 MySQL 比标准更“强”的地方。

事务与 MVCC 细节见 [事务与 MVCC](/java/mysql/transaction-mvcc)。

## MVCC：读写怎么不互斥

- **多版本并发控制**：每行数据保留多个版本（隐藏列 + undo log 版本链），读走快照，写产生新版本。
- **read view**：事务读取时生成“可见性视图”，决定能看到哪个版本。
  - RC：**每次 select** 都生成新 read view → 能读到别人已提交的最新（不可重复读）。
  - RR：**事务第一次 select** 时生成 read view，全程复用 → 可重复读。
- 易错点：MVCC 只解决**普通 select** 的并发读。**当前读**（`select ... for update`、update、delete）不走 MVCC，走锁。

## 锁

- **行锁三类**：记录锁（锁单行）、间隙锁（锁区间，防幻读）、临键锁（记录 + 前间隙，RR 默认）。
- **意向锁**：表级意图锁，快速判断表里有没有行锁，避免逐行扫。
- **死锁**：两个事务互相等对方释放锁。InnoDB 有死锁检测（`innodb_deadlock_detect`，默认开）。

锁细节见 [MySQL 锁](/java/mysql/lock)。

## 日志：redo / undo / binlog

| 日志 | 作用 | 属于 |
|------|------|------|
| redo log | 崩溃恢复（持久性），WAL 先写日志再改磁盘 | InnoDB |
| undo log | 回滚 + MVCC（原子性 + 多版本） | InnoDB |
| binlog | 主从复制 + 数据恢复 | Server 层（所有引擎） |

易错点：redo log 是**物理日志**（记“哪页哪个 offset 改成什么”），binlog 是**逻辑日志**（记“执行了什么 SQL”）。**两阶段提交**（redo prepare → 写 binlog → redo commit）保证两者一致，这是“主从切换不丢数据”的基础。
