# MySQL 索引

> 面试高频。索引题考察四件事：**为什么是 B+ 树、聚簇 vs 二级、覆盖索引、什么时候失效**。本文按问答组织，每题「答 + 追问 + 易错点」。

## 思考锚点

在数据库里查数据，如果每次都要扫描全表，数据量大的时候会非常慢。索引就是解决这个问题的——它像书的目录，能帮我们快速定位到需要的数据。

但索引不是免费的：它占用额外存储空间，会降低写入速度（每次插入/更新都要维护索引），而且并不是所有查询都能用上索引（比如 `LIKE '%xxx'`、函数操作等）。

本文要讲清楚 MySQL 为什么选 B+ 树做索引、聚簇索引和二级索引的区别、覆盖索引是什么，以及哪些情况会导致索引失效。

## 体系速览

```
索引分类
├── 数据结构：B+ 树（默认）/ Hash（Memory 引擎 + InnoDB 自适应哈希 AHI）
├── 物理存储：聚簇索引（叶子存整行）/ 二级索引（叶子存主键）
├── 字段个数：单列 / 联合
└── 特性：主键 / 唯一 / 普通 / 全文
```

核心：InnoDB 的索引就是 B+ 树。理解 B+ 树就理解了查询成本从哪来。

## Q1：为什么 MySQL 索引用 B+ 树？

**答**：B+ 树在**磁盘 IO** 上最优，三个原因：

1. **树矮 = IO 少**：B+ 树是多叉树（不像二叉树/红黑树瘦高），3 层就能存千万级数据。树高 ≈ 查询的磁盘 IO 次数，矮就快。
2. **非叶子节点只存 key 不存数据**：一个节点能塞更多 key，扇出更大，树更矮。
3. **叶子节点串成有序链表**：范围查询（`between`、`>`）定位起点后沿链表扫即可；B 树每个节点都存数据，范围查询要中序遍历整棵树，IO 多。

**追问**：为什么不用 Hash 索引？→ Hash O(1) 等值查询确实快，但**不支持范围查询、排序、最左前缀匹配**。所以 InnoDB 主索引不选 Hash（AHI 是它自己在 B+ 树之上加的内部优化，用户不可选）。

**易错点**：答"B+ 树查询快"不够——更准确说是**"磁盘 IO 少"**。纯内存场景 B+ 树不一定比红黑树快，它的优势在磁盘。

## Q2：聚簇索引 vs 二级索引？

**答**：
- **聚簇索引**：叶子节点**直接存整行数据**。一张表只有一个，通常是主键。数据和主键索引一体化。
- **二级索引（辅助索引）**：叶子节点只存**主键值**。走二级索引查到主键后，还要**回表**到聚簇索引拿整行。

**回表**：二级索引 → 主键 → 再查聚簇索引拿数据。一次查询 = 两次 B+ 树查找。

**追问**：为什么 InnoDB 主键建议**自增整型**？→ 聚簇索引按主键有序排列。自增主键插入时**顺序追加到叶子节点尾部**；UUID/随机主键插入会触发**页分裂**（数据要挪到中间），写放大、产生碎片。

**易错点**：**MyISAM 没有聚簇索引**——它的数据与索引分离，主键索引和二级索引叶子都存行地址。所以 MyISAM 主键查询并不比二级索引快。"主键查询最快"是 InnoDB 独有的特性。

## Q3：什么是覆盖索引？

**答**：查询的列**全部包含在索引里**时，二级索引叶子节点直接返回数据，**不用回表**。这叫覆盖索引。

```sql
-- 联合索引 (a, b)
SELECT a, b FROM t WHERE a = 1;        -- 覆盖索引，不回表
SELECT a, b, c FROM t WHERE a = 1;     -- c 不在索引里，必须回表
```

**易错点**：`explain` 里 `Extra: Using index` 才是覆盖索引；`Using index condition` 是**索引下推（ICP）**，不是覆盖。两者名字像但完全是两回事。

## Q4：联合索引和最左前缀原则？

**答**：联合索引 `(a, b, c)` 按 a→b→c 顺序建 B+ 树。能用上索引的前提是**从最左列开始连续使用**：

- `WHERE a=1` ✅ 用 a
- `WHERE a=1 AND b=2` ✅ 用 a, b
- `WHERE a=1 AND b=2 AND c=3` ✅ 全用
- `WHERE b=2` ❌ 不用（跳过了 a）
- `WHERE a=1 AND c=3` ⚠️ 只用 a（中间跳过 b，c 接不上）

**范围查询会中断后续列**：`WHERE a=1 AND b>5 AND c=3` 中 `b>5` 是范围，**之后的 c 用不上索引**。

**常见误解**：以为"WHERE 里字段的书写顺序"决定是否命中——错。**SQL 优化器会自动调整顺序**，`WHERE b=2 AND a=1` 和 `WHERE a=1 AND b=2` 效果一样。最左前缀看的是**索引列的定义顺序**，不是 SQL 里写的顺序。

## Q5：索引失效有哪些场景？

**答**（高频背诵点）：

1. **对索引列做函数/计算**：`WHERE YEAR(create_time)='2024'`、`WHERE id + 1 = 10`
2. **隐式类型转换**：列是 varchar 却写 `WHERE phone = 13800000000`（数字 vs 字符串），优化器把每行转成数字比对
3. **左模糊**：`WHERE name LIKE '%张'`（右模糊 `'张%'` **能**走索引）
4. **`OR` 两边不全有索引**
5. **`!=`、`NOT IN`、`NOT LIKE`**（优化器通常判断为走全表更划算）
6. **违反最左前缀**或**范围查询后的列**
7. **`ORDER BY` 顺序与索引不符** → `Using filesort`

**易错点**：`LIKE '张%'`（右模糊）**能**走索引——只有**左**模糊才失效。这是面试套路题，别答"LIKE 一定不走索引"。

## Q6：什么时候该/不该建索引？

**答**：

**该建**：
- 主键、唯一约束（自动建）
- 经常出现在 `WHERE` / `JOIN` / `ORDER BY` / `GROUP BY` 的列
- 区分度高（cardinality 接近表行数）

**不该建**：
- 区分度极低（如性别只有两值，优化器会放弃索引直接全表扫）
- 表太小（全表扫比走索引还快）
- 频繁增删改的列（索引维护成本：每次写都要维护 B+ 树）
- 不出现在 WHERE 里的列

**易错点**："区分度低就一定不建"——不绝对。**覆盖索引**即使区分度低也可能值得建（避免回表）。要看实际查询组合判断。

## Q7：怎么用 EXPLAIN 看索引用没用？

**关键列**：

| 列 | 看什么 |
|---|---|
| `type` | 访问类型。`const`/`eq_ref`/`ref`（好）→ `range`（范围，可接受）→ `index`（扫整棵索引树）→ `ALL`（全表扫描，最差） |
| `key` | 实际使用的索引（`NULL` = 没走索引） |
| `rows` | 估算扫描行数（越少越好） |
| `Extra` | `Using index`（覆盖）/ `Using where`（过滤）/ `Using filesort`（额外排序，警惕）/ `Using temporary`（临时表，警惕） |

**易错点**：`key` 显示了索引但 `rows` 接近全表行数——说明优化器选了索引但实际几乎扫全表，可能还不如 `ALL`。**不能只看 key 有没有值，要结合 rows 判断**。

## 易错点速查表

| 知识点 | 关键 |
|---|---|
| B+ 树优势 | 矮（IO 少）+ 叶子链表（范围快）；本质是**磁盘 IO** 优化，不是内存查询快 |
| 聚簇 vs 二级 | 二级索引要回表；MyISAM 无聚簇索引 |
| 覆盖索引 | `Extra: Using index`；和 `Using index condition`（ICP）不是一回事 |
| 最左前缀 | 看索引列定义顺序，不是 SQL 书写顺序；范围查询后中断 |
| 左/右模糊 | `'%张'` 失效，`'张%'` 能走索引 |
| 主键建议 | InnoDB 用自增整型（避免页分裂） |
| EXPLAIN | 不能只看 `key`，要结合 `rows` 和 `Extra` |
