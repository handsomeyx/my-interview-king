# MySQL 锁

> MySQL 锁面试核心：**行锁 / 间隙锁 / Next-Key Lock 的区别，以及死锁怎么处理**。这块和事务隔离（见 [事务 MVCC](./transaction-mvcc)）紧密相关——RR 防幻读就靠间隙锁。本文按问答，每题答 + 易错点。

## 思考锚点

并发事务同时操作数据库时，需要一种机制来协调它们对共享资源的访问顺序。如果不加控制，两个事务可能同时修改同一行数据，导致数据不一致。

MySQL InnoDB 提供了多种锁机制：从粗粒度的表锁到细粒度的行锁，再到防幻读的间隙锁和 Next-Key Lock。不同锁的适用场景不同，选错了会导致性能问题甚至死锁。

本文要讲清楚 MySQL 有哪些锁、它们的适用场景、Gap Lock 的特殊之处，以及死锁的产生原因和预防方法。

## Q1：MySQL 有哪些锁？

**答**：按粒度从大到小：

| 锁 | 粒度 | 场景 |
|---|---|---|
| 全局锁 | 整个数据库 | `FLUSH TABLES WITH READ LOCK`，备份用 |
| 表锁 | 表 | `LOCK TABLES`，或 DDL |
| 行锁 | 行 | InnoDB 默认，**只在 RR/RC + 索引条件**下生效 |

**易错点**：InnoDB 的"行锁"**必须走索引**——没索引退化为**表锁**（扫全表每行都锁）。这是高频坑："以为加了行锁其实是表锁，全表卡住"。

## Q2：行锁的几种类型？

**答**：InnoDB 行锁有三种：

1. **Record Lock（记录锁）**：锁**单行**（索引上的某条记录）。
2. **Gap Lock（间隙锁）**：锁**两行之间的间隙**（不含记录本身），防 insert 到间隙里。只在 **RR** 隔离级别出现。
3. **Next-Key Lock**：Record + Gap，锁**一个左开右闭区间** `(a, b]`。InnoDB 在 RR 下默认用它。

**作用**：
- Record Lock 防"同行的并发改"。
- Gap Lock / Next-Key Lock 防"范围内 insert"——这就是 **RR 防幻读**的原理（当前读场景）。

**易错点**：Gap Lock **只在 RR** 有（RC 没有，所以 RC 会幻读）。Gap Lock 之间**不互斥**——多个事务可以同时持有一个间隙的 Gap Lock，因为它们目标一致（都是"防别人 insert"）。

## Q3：共享锁（S）和排他锁（X）？

**答**：
- **S（共享锁，读锁）**：`SELECT ... LOCK IN SHARE MODE`。允许多个事务同时读，但都不许改。
- **X（排他锁，写锁）**：`SELECT ... FOR UPDATE` / `UPDATE` / `DELETE`。独占，其他事务的带锁读和写都阻塞。

兼容性：S-S 兼容；S-X、X-X 互斥。

**易错点**：普通 `select`（快照读）**不加锁**（走 MVCC），所以不会被 X 阻塞。只有"当前读"（`for update` / `lock in share mode` / 写操作）才涉及 S/X 锁。

## Q4：意向锁（IS/IX）是什么？

**答**：表级锁，**给表加行锁前先加意向锁**，目的是**快速判断"表里有没有行被锁"**。

- 想加行 S 锁 → 先加表 IS（意向共享）
- 想加行 X 锁 → 先加表 IX（意向排他）

**为什么**：如果没有意向锁，想给表加表锁时要逐行检查有没有行锁——太慢。有意向锁后，看表有没有 IS/IX 就知道。

**易错点**：意向锁是**表级**的，且**意向锁之间兼容**（IS-IS、IS-IX、IX-IX 都兼容），它只和"表锁"互斥。InnoDB 自动加，业务不用手动管。

## Q5：死锁怎么产生和处理？

**答**：

**产生**：两个事务互相持有对方想要的锁。
```
事务A：锁了行1，等行2
事务B：锁了行2，等行1
→ 互相等，死锁
```

**处理**：
- **InnoDB 自动检测**：`innodb_deadlock_detect=on`（默认开），检测到死锁**主动回滚代价小的事务**。
- **锁等待超时**：`innodb_lock_wait_timeout`（默认 50s），超时放弃。

**避免**（编码实践）：
1. **统一加锁顺序**（如按主键升序加锁），避免交叉等待。
2. **事务尽量短**，减少持锁时间。
3. 大事务拆小。
4. 降低隔离级别（RR → RC，间隙锁少了，死锁概率降）。

**易错点**：死锁不是 bug，是**并发事务的正常现象**。重点是怎么**减少发生 + 快速恢复**，不是完全消除。

## Q6：乐观锁 vs 悲观锁？

**答**（应用层概念，不是 MySQL 内置）：
- **悲观锁**：假设会冲突，先锁再操作（`for update`）。强一致，性能差。
- **乐观锁**：假设不冲突，提交时检查版本号（`UPDATE ... SET version=version+1 WHERE id=? AND version=?`）。性能好，失败重试。

**取舍**：冲突少 → 乐观锁（无锁高并发）；冲突多 → 悲观锁（避免大量重试）。

**易错点**：乐观锁的 `UPDATE` 那一句要**判断 affected rows**——返回 0 说明版本号变了（别人改过），要重试或报错。很多人写了乐观锁但没处理"更新失败"，等于没锁。

## 易错点速查表

| 知识点 | 关键 |
|---|---|
| 行锁走索引 | 没索引退化为表锁（全表锁）|
| 三种行锁 | Record（行）/ Gap（间隙，仅 RR）/ Next-Key（间隙+行，RR 默认） |
| Gap Lock | 仅 RR；Gap 之间不互斥 |
| 快照读不加锁 | 普通 select 走 MVCC，不被 X 阻塞 |
| 意向锁 | 表级、自动加、意向锁之间兼容 |
| 死锁 | InnoDB 自动检测回滚；统一加锁顺序预防 |
| 乐观锁 | UPDATE 判断 affected rows，0 = 失败要重试 |
