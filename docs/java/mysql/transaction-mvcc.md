# MySQL 事务与 MVCC

> MySQL 事务面试三大核心：**ACID、四种隔离级别 + 对应并发问题、MVCC 怎么实现快照读**。很多人能背"RR 解决幻读"，但追问"MVCC 的 ReadView 什么时候生成""RR 真的完全防住幻读吗"就答不上。本文按问答，每题答 + 易错点。

## 思考锚点

多个事务同时操作数据库时，可能出现读到别人未提交数据（脏读）、同一事务两次读结果不同（不可重复读）、查询结果集行数变化（幻读）等问题。数据库必须设计一套机制来保证并发下的数据正确性。

MySQL InnoDB 用「锁 + MVCC」组合解决这些问题：写操作加锁保证隔离性，读操作走 MVCC 快照读避免阻塞。但不同隔离级别下 MVCC 的行为不同，快照读和当前读混用还可能出现看似矛盾的现象。

本文要讲清楚 ACID 四大特性、四种隔离级别分别解决什么问题、MVCC 的三件套实现原理，以及 RC 和 RR 下 MVCC 的核心区别。

## Q1：ACID 是什么？

**答**：
- **A（Atomicity，原子性）**：事务要么全做要么全不做。靠 **undo log** 回滚实现。
- **C（Consistency，一致性）**：事务执行前后数据合法（约束、规则不破坏）。一致性是**目的**，AID 是手段。
- **I（Isolation，隔离性）**：并发事务互不干扰。靠 **锁 + MVCC** 实现。
- **D（Durability，持久性）**：提交后永久。靠 **redo log** 实现（崩溃恢复）。

**易错点**：一致性是"结果"，AID 是"保障手段"。很多人把 C 当成独立机制——其实 C 是 A+I+D 共同保证的最终效果（再叠加应用层约束）。

## Q2：四种隔离级别 + 并发问题？

**答**：并发事务有三个问题，隔离级别递增解决：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| 读未提交（RU）| 可能 | 可能 | 可能 |
| 读已提交（RC）| × | 可能 | 可能 |
| 可重复读（RR，**InnoDB 默认**）| × | × | 可能（InnoDB 大部分场景已防） |
| 串行化（Serializable）| × | × | × |

三个问题：
- **脏读**：读到别的事务**未提交**的数据。
- **不可重复读**：同一事务里两次读同一行结果不同（别的事务 **update** 提交了）。
- **幻读**：同一事务里两次范围查询结果集行数不同（别的事务 **insert/delete** 提交了）。

**易错点**：不可重复读 vs 幻读的区别——前者是**某行被改**，后者是**行数变了**（新增/删除）。这两个常被混。

## Q3：MVCC 是什么？怎么实现？

**答**：MVCC（Multi-Version Concurrency Control，多版本并发控制）——让读不加锁也能保证一致性，提升并发。

**InnoDB 实现靠三件套**：
1. **行的隐藏列**：每行有 `trx_id`（最近修改它的事务 ID）、`roll_pointer`（指向 undo log 的上一版本）。
2. **undo log 版本链**：每次 update 生成旧版本，通过 roll_pointer 串成链（历史版本）。
3. **ReadView（读视图）**：读时生成的一致性快照，记录"当前活跃事务列表"。

**读取流程**：拿到一行，沿版本链比对 `trx_id` 和 ReadView，找到"对当前事务可见"的版本（即该版本的事务在 ReadView 生成时已提交）。

## Q4：RC 和 RR 的 MVCC 区别？

**答**：核心区别在 **ReadView 生成的时机**：

- **RC（读已提交）**：**每次 select** 都生成新 ReadView。所以能看到别的事务刚提交的更新——产生"不可重复读"。
- **RR（可重复读）**：**事务第一次 select** 时生成 ReadView，整个事务复用。所以多次读结果一致——"可重复读"。

**易错点**：RR 的"可重复读"靠的是 **ReadView 复用**（一次快照定死），**不是锁**。这是面试筛人点——很多人以为 RR 靠锁保证可重复读，其实是 MVCC 的快照机制。

> 🤔 停下来想想：ReadView 在 RC 和 RR 下生成时机不同，这带来了什么行为差异？

## Q5：快照读 vs 当前读？

**答**：
- **快照读**：普通 `select`，读 MVCC 的快照版本，**不加锁**。
- **当前读**：`select ... for update`、`update`、`delete`、`insert`，读**最新已提交版本**，并**加锁**。

**易错点**：RR 下快照读用 MVCC（防不可重复读），但**当前读读的是最新值**——所以 RR 下两次普通 `select` 结果一样，但 `select for update` 可能看到新数据。混合用会产生"似乎又不一致"的现象。

## Q6：RR 真的解决幻读了吗？

**答**：**部分解决**，不是完全解决。

- **快照读**：靠 MVCC，ReadView 定死，**防住幻读**（每次 select 看同一快照）。
- **当前读**：靠**间隙锁（Gap Lock）/ Next-Key Lock**，锁住范围防止 insert，**也能防住**幻读。

但**混合使用会破防**：先 `select`（快照读），再 `select for update`（当前读），中间别的事务 insert 了，当前读会看到新行——"幻像"又出现。

**易错点**："InnoDB RR 完全解决幻读"是常见错误答案。准确说法：**RR 在单纯快照读或单纯当前读场景防住幻读；快照读 + 当前读混用仍可能出现幻读**。要彻底防住，全程用 `for update` 当前读 + 间隙锁。

## 易错点速查表

| 知识点 | 关键 |
|---|---|
| ACID 的 C | 是结果，靠 AID + 应用约束保证 |
| 不可重复读 vs 幻读 | 行被改 vs 行数变（新增/删除） |
| InnoDB 默认 | RR（可重复读） |
| MVCC 三件套 | 行隐藏列 + undo log 版本链 + ReadView |
| RC vs RR | ReadView 每次 select 生成 vs 事务首次 select 生成 |
| RR 可重复读 | 靠 ReadView 复用（快照），不是锁 |
| 快照读 vs 当前读 | 普通 select 不加锁；for update/update 读最新 + 加锁 |
| RR 幻读 | 快照读/当前读各自防；混用仍可能幻读 |
