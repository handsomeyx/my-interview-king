# Redis 持久化与缓存问题

> Redis 面试下半场：**持久化（RDB/AOF 怎么选）+ 缓存三大问题（穿透/击穿/雪崩）+ 缓存一致性**。这三块是工程实战高频题，光背概念不够，要能说清"什么场景选什么方案、为什么"。本文按问答，每题答 + 易错点。

## 思考锚点

Redis 是内存数据库，速度快但数据存在内存里——如果断电或重启，数据就丢了。所以必须要有持久化机制把内存数据存到磁盘上。但持久化又会带来性能开销，需要在数据安全和性能之间做取舍。

另外，当 Redis 作为缓存使用时，还面临三大经典问题：缓存穿透（查不存在的数据）、缓存击穿（热点 key 过期）、缓存雪崩（大量 key 同时过期或 Redis 宕机）。

本文要讲清楚 RDB 和 AOF 的区别与选型、缓存三大问题的解决方案，以及缓存和数据库之间的一致性保证。

## Q1：RDB 和 AOF 区别？怎么选？

**答**：

| 维度 | RDB | AOF |
|---|---|---|
| 原理 | 定时全量快照（内存 dump 成文件） | 追加每条写命令到日志 |
| 文件 | 紧凑、小 | 大（命令日志） |
| 恢复速度 | 快（直接加载） | 慢（重放命令） |
| 数据安全 | 丢最近一次快照后的数据 | 取决于刷盘策略（最多丢 1 秒） |
| 触发 | save/bgsave/配置间隔 | 实时追加 |

**AOF 三种刷盘策略**（`appendfsync`）：
- `always`：每条命令刷盘，最安全但最慢（基本不用）。
- `everysec`：每秒刷盘（**默认，推荐**），最多丢 1 秒。
- `no`：交由 OS，不可控。

**取舍**：
- 只做缓存、能容忍少量丢失 → RDB（恢复快、文件小）。
- 数据重要（订单、会话）→ AOF everysec。
- 生产常用 **混合持久化**（`aof-use-rdb-preamble yes`，4.0+）：AOF 文件前半是 RDB 全量，后半是增量命令。兼顾恢复快和安全，**当前主流**。

**易错点**：RDB 的 `bgsave` 用 **fork 子进程 + COW（Copy-On-Write）**，fork 瞬间会短暂阻塞（大内存实例 fork 慢）。不是"RDB 完全无影响"。

## Q2：缓存穿透？

**答**：**查根本不存在的数据**（如恶意请求 id=-1），缓存没有、数据库也没有，每次都打到 DB。

**方案**：
1. **缓存空值**：DB 查不到也缓存 `null`（设短过期），下次直接拦。简单，但不防"随机不同 id 攻击"。
2. **布隆过滤器**：请求先过布隆过滤器，不存在直接拦。空间高效，但有误判率（说"存在"可能不存在，说"不存在"一定不存在）。

**取舍**：少量穿透用空值；海量 key 攻击用布隆过滤器。

**易错点**：缓存空值的 key 要**设过期时间**，否则空值堆积占满内存。

## Q3：缓存击穿？

**答**：**单个热点 key 突然过期**，瞬间大量请求穿透到 DB。

**方案**：
1. **互斥锁**：缓存失效时只让一个请求查 DB 重建缓存，其他等待。强一致但吞吐降。
2. **逻辑永不过期**：物理上不设过期时间，后台异步更新。高可用但有短暂脏数据。
3. **热点 key 永不过期 + 主动刷新**（配合定时任务）。

**易错点**：互斥锁要保证"查 DB + 写缓存"在锁内，否则锁白加。

## Q4：缓存雪崩？

**答**：两种情况：
1. **大量 key 同时过期**（如批量预加载时设了相同 TTL）。
2. **Redis 宕机**，所有请求打 DB。

**方案**：
- 防大量同时过期：**过期时间加随机值**（如 `ttl + random(60s)`），打散。
- 防 Redis 宕机：**集群 / 哨兵高可用** + **下游限流降级**（DB 扛不住时限流保命）。

**易错点**：击穿是"单热点 key"，雪崩是"大量 key"。两者方案不同——击穿用互斥锁，雪崩用 TTL 随机 + 高可用。别混。

> 🤔 停下来想想：三者的核心区别是什么？各自的解法思路有什么本质不同？

## Q5：缓存和数据库一致性？

**答**：主流是 **Cache Aside（旁路缓存）**：
- 读：先查缓存，没有查 DB 再回填。
- 写：**先更 DB，再删缓存**（不是更新缓存）。

**为什么删而不是更新缓存**：更新缓存有并发问题（A 先算出新值、B 后算出旧值，B 后写覆盖 A）；删缓存是幂等的，下次读自然回填最新值。

**追问：先删缓存还是先更 DB？**→ **先更 DB 再删缓存**。先删缓存有坑：删了缓存、还没更 DB 时，另一个请求读到旧 DB 值又回填缓存，缓存永远是旧的。

**追问：先更 DB 再删缓存就一定一致吗？**→ 不绝对。极端场景：删缓存失败、或主从复制延迟。生产用**延迟双删**（更 DB → 删缓存 → 延迟再删一次）或**订阅 binlog 异步删**（Canal）兜底。

**易错点**："先删缓存再更 DB"是常见错误写法，并发下必然脏数据。**正确顺序是先 DB 后删缓存**。

## Q6：强一致能做到吗？

**答**：**缓存 + DB 加起来无法做到强一致**（除非加分布式锁串行化，性能崩）。缓存本质是"用一致性换性能"，能保证**最终一致**就够。

如果业务必须强一致（如资金），**别用缓存**，直接走 DB。这是架构取舍——别为了性能强上缓存又抱怨不一致。

## 易错点速查表

| 问题 | 关键 |
|---|---|
| 持久化选型 | 缓存用 RDB；重要数据 AOF everysec；主流混合持久化 |
| RDB bgsave | fork 子进程 + COW，fork 瞬间短暂阻塞 |
| 穿透 | 查不存在的 → 空值缓存（带 TTL）/ 布隆过滤器 |
| 击穿 | 单热点 key 过期 → 互斥锁 / 逻辑永不过期 |
| 雪崩 | 大量 key 同时过期或 Redis 挂 → TTL 随机 + 高可用 + 限流降级 |
| 击穿 vs 雪崩 | 单 key vs 大量 key，方案不同 |
| 一致性写顺序 | 先更 DB 再删缓存（不是先删） |
| 强一致 | 缓存做不到强一致；资金类别上缓存 |
