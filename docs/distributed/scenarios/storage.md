# 数据持久化和异步层
## 概述

这章节主要帮大家梳理一下请求进入到数据持久化和异步层的结构 ，对于一些概念和解决方案不会展开来讲，需要大家有一定的基础。同时在梳理的过程中，也会适当提问引发大家的思考。

用户发送请求后，并不是直接打到数据库的，同学在做一些个人项目的时候，容易忽略“请求中间层”，直接让应用服务器调用数据库，这在小流量场景下没问题，但一旦进入高并发场景，瞬间就会崩溃，而MQ就是从应用层到数据层的关键缓冲带，起到“异步解耦，削峰填谷”的作用。

先跟大家讲明白，请求到MQ这一个阶段到底是怎么处理的。咱们以用户下单请求为例。

- **第一步**：用户应用服务器接受到请求，**请求先会到达应用服务器**，它回显做基础校验，用户是否登录、商品是否有库存、订单参数是否合法等。
- **第二步**：接下俩就是要区分**核心操作和非核心操作，拆分同步和异步流程**。下单请求的核心流程是写入订单数，这是必须同步执行、确保成功的；而非核心流程像”发送下单成功通知“，这些流程不影响用户看到”下单成功“的结果完全可以异步执行。如果没有MQ，应用服务器会同步执行者三个操作，用户要等所有操作完成，这时候响应可能会很长，同时服务故障了，那可能导致整个下单流程失败
- **第三步**：应用服务器向MQ发送异步消息，核心流程（写入订单数据）执行完成后，应用服务器会向MQ发送两条异步消息，一条是“库存更新消息”，携带商品ID、扣减数量等信息，另一条是“通知发送消息”，携带用户手机号、订单号等信息。这边有个考点，必须开启**生产者确认机制**，避免消息丢失
- **第四步**：MQ收到消息后，不会直接转发到下游服务，而是先将消息持久化。我项目的话使用kafka，那就是用kafka的日志进行持久化，将消息持久化到磁盘。**防止MQ宕机导致消息丢失**，所以当问到怎么保证消息不丢失的话，**持久化**是关键的步骤之一。
- **第五步**：MQ持久化消息后，会根据预设的路由规则，将“库存更新消息”推送给通知服务，下游服务会监听MQ对应的队列，收到消息后异步执行处理逻辑：库存服务扣减库存，通知服务发送短信/推送通知。处理完成后下游服务会向MQ发送“消费者确认信号”，MQ收到确认后，才会删除对应的消息，没收到则会重新推送。

讲到这里，总结一下请求——MQ的流程：用户发起请求 → 应用服务器接收并校验请求 → 执行核心同步流程 → 向MQ发送异步消息（开启生产者确认） → MQ接收并持久化消息 → MQ推送消息给下游服务 → 下游服务异步处理并确认消息。

在MQ这层也会有相应的考察点：
- **消息丢失**：你要从生产者，消息队列，消费者三个情况考虑。
- **消息重复消费**：幂等性问题，常用唯一索引解决，还有吗？
- **高可用性**：宕机了怎么办？
- **消息顺序性**：比如下单、支付、再发货，必须按这个顺序，怎么确保消息处理是按这个顺序呢？
- **架构**：你使用是MQ的架构是怎么样的，能画出来吗？

基本上你能梳理完这个流程，回答上这些考察点，我认为你没有问题了。

接下来就是要进行数据库的操作了，经过我多轮的面试感觉下来，这在数据持久化和异步层考核是重中之重。我将从最基础的单个数据库场景帮你梳理，一步一步演变成多级的缓存架构。

假设你做一个项目，只有一个Mysql数据库。一开始用户量少，这个架构完全没问题，我们的数据读写完全都可以走一个库，简单又省心，但当你逐渐发展用户量上去到几千、几万用户量，单体数据库就会以下问题：
- **读写冲突**：你想想，你的项目肯定是有查询功能和添加xx的功能的吧，读和写如果都在一个库里进行操作，如果写的多，读就需要等，反之亦然。同时，MYsql我们最用的InnoDB引擎默认是行锁，但如果我们执行批量写操作，会升级为表锁，此时所有的读操作都会被阻塞，接口响应时间突突突就上去了。	**留个小问题**，有些同学觉得到这里加索引就可解决，那理解就太浅了，索引本质是优化查询效率，解决不了读写抢占资源的本质。
- **数据持久化风险**：万一我这个数据库出现故障怎么办，我就只有一份数据呀，那不完了。有些同学说可以用binlog日志来恢复，但是恢复要时间哦，且恢复期间服务无法正常提供，时间就是钱啊！！
- **异步层与数据库的联动隐患**：我们很多项目会用异步任务处理非核心流程，比如用户下单后，异步发送通知、更新库存。但如果只有单个数据库，异步任务的执行会进一步加剧数据库的压力——比如下单是写操作，异步更新库存也是写操作，两个写操作同时命中同一个数据库，会导致锁竞争更激烈，甚至出现“数据不一致”。比如用户下单成功，但异步库存更新失败，导致商品超卖，这就是典型的“异步与持久化配合不当”的问题。更麻烦的是，单个数据库无法做“读写分离”，异步任务的读操作（比如查询当前库存）也会占用写操作的资源，进一步拖慢整体性能。

![单个数据库的架构](/images/java-backend/scenarios/5.png)

为了解决读写冲突，那我们干脆就把读和写的只能分出来呗，扩展数据库，让不同的数据库各司其职，主库负责写操作，所有增删改查统一给主库，然后主库负责数据的持久化和实物保证，确保写操作的一致性和可靠性。一个或多个从库负责读。这样不就实现了读写分离。同样的，我要是主库故障了，我从库是不是可以顶上来，服务不就不会中断了，同样的异步层的压力也减少了，一箭三雕！但是，从库为能替代主库呀，他们数据是一致的吗？这就又冒出**数据一致性的问题啦**，解决方法是主从复制，这里不再延伸哈，不懂的小伙伴可以去了解具体的原理。

看到这，很多同学可能会觉得：主库负责写，从库负责读，读写分离搞定了，数据库的压力也分摊了，那是不是请求到数据库这层，就彻底没问题呢？举个真实应用场景的例子，假设你的项目活力，用户量涨到10万+，每天的商品请求有上百万次——要知道，即使是从库，也是基于磁盘存储的，磁盘IO读写比内存慢多了（毫秒vs微秒），即使你多开了几个从库，但每个从库读数据的速度还是很慢，面对海量的买东西的人，还是可能被压垮。

- 这就是主从分离无法解决的核心的痛点：**读请求量远超从库的承载能力，磁盘IO成为新的性能瓶颈**。我们到从库执行查询操作，本质还是从磁盘读取数据，一次查询大概在10-50毫秒，如果有1000次这样的查询，从库的IO就会被打满，后续查询请求会排队等待，响应时间暴涨。

- 痛点二，主从复制也是有延迟的，当我们海量读请求被放大后，主从复制原本毫秒级的延迟可能被放大到秒。可能会出现用户刚发布的商品（主库已写入），在从库查询不到，或者用户刚下单成功，查询订单状态还是“未支付”——这种数据不一致的情况，会直接影响用户体验，也是大厂绝对不能容忍的。

- 另外成本方面的考量，以上问题你有可能会想说，那我一直增加从库不就得了。但是从库越多，主从复制的复杂度越高，运维成本也高（因为你要监控主从同步状态，处理从库故障），多从库是抵消且高成本的方案。

那么，缓存的出现就彻底解决了这个问题了，我们在获取数据的时候也顺便缓存起来。这样下次请求还查这个，那直接拿缓存不就方便多了。

那缓存放在哪呢，很多同学可能会把缓存存在服务器的本地缓存中，比如java的HashMap当本地缓存，简单还不用部署中间件，但只能用于小流量场景，一旦你的应用部署了多个实例，本地缓存就会出大问题：每台的服务器的缓存都是独立的数据，无法进行同步了。比如用户在A服务器查询过商品，A服务器的本地缓存存了数据，但用户下次请求被分配到了B服务器，B服务器缓存没有该数据，还是要去访问从库，缓存的作用就大打折扣了；更麻烦的是，一旦某台服务器的缓存更新了，其他服务器的缓存还是旧数据会导致数据不一致。

所以，咱们在实际开发中，缓存肯定不会存本地，而是用分布式缓存集群来存储的，最常用的就是Redis集群，简单说，就是部署多态Redis服务器，组成一个集群，然后所有的应用实例都去这个集群里读写缓存，这样一来不管用户的请求被分到哪台服务器，访问的都是同一个缓存集群，数据一致性，而且能承接更多的读请求。

这样子看上去是不是大功告成了，有了缓存之后本地数据库的问题是不是都可以被解决了？并不是，缓存也算是一个“数据库”呀，所以我们也要考虑缓存部署的可用性和一致性。

Redis常用的保证可用性的机制有，主从复制和哨兵机制。但是集群间节点的数据同步也会有延迟，就跟Mysql一样。同时集群的运维成本复杂度也提高了，要维护多台Redis节点，监控节点状态，处理节点故障，这些都需要额外的运维成本。这就需要大家掌握Redis集群的部署方式，哨兵机制的作用了。

在解决了缓存的存储问题，接下来就是第二个关键问题：数据库更新后，缓存怎么去同步呢？比如用户修改了商品价格，如果缓存里的商品价格还是旧的，用户查询直接拿缓存就是错误的价格了。常见的缓存更新策略有两种，面试的时候一定要说清楚区别和优劣。

- **更新数据库后，同步更新缓存**：简单，但是存在两个问题，如果更新数据库成功，更新缓存失败，缓存还是旧数据；二是多个请求同时更新，会出现缓存覆盖的问题。
- **更新数据库后，再删除缓存**：这样即使下次用户查询该商品，缓存未命中会先去从库拿最新数据，再把数据存入缓存。这种方式能避免同步更新的缺陷，但也有一个小问题，如果删除缓存后，查询请求先于缓存更新完成，还是会查询到旧数据（从库可能还没同步主库的 更新），这就需要结合延迟双删等补偿机制了。

讲完存储和同步的问题了，到这里缓存的问题都解决完了吗？当然没有，还有一个容易被忽略，但非常关键的问题：缓存难道没有上限吗？要知道缓存是基于内存存储的，而内存容量是有限的，不管是单台Redis还是Redis集群，内存都有上限，不可能无限制存储数据。如果一直往缓存里村数据，不做限制，迟早会内存溢出（OOM），导致Redis崩溃，所有请求失效，压力都到数据库上了。

那咋解决缓存上限的问题呢？这就涉及到内存淘汰策略了，常见的有LRU、LFU策略。这里不清楚的请大家自习了解一下。

缓存的基本问题咱解决了，但缓存层还有三个致命的问题，**缓存穿透，缓存击穿，缓存雪崩**，接下来我来分别讲讲：
- **缓存穿透**；简单讲就是用户查询的数据，缓存没有，数据库也没有。比如有人故意查询一个不存在的商品ID(比如ID为-1，ID为999999999）超出正常范围，缓存没有，所以每次请求都穿透缓存打到数据库上，如果是恶意攻击，每秒发送成千上万次这样的请求，数据库就会被直接压垮。分析一下为什么吗会出现缓存穿透？**一是业务逻辑漏洞**，用户输入了非法ID，后端没校验直接查询，**二是恶意攻击**，攻击这故意构造不存在的key批量发起请求，利用缓存穿透拖垮数据库，很多同学做项目时，只考虑**缓存击穿和缓存未命中**的情况，还忽略了**数据库完全没有数据**的场景。———— 所以，再说解决方法时，先说**非法请求校验**，在请求到达缓存和数据库之前，先做一层校验，比如校验商品ID的格式（必须是正整数）、范围（不能超出正常商品ID的范围），对于非法请求，直接返回错误。然后就是**缓存空值和布隆过滤器**的抉择，**你在讲述时一定要体现你对两个技术均有思考，为什么选择A而不选择B**。
- **缓存击穿**：缓存击穿本质是**缓存没有，但数据库有数据**，而且是高频访问的key，因为缓存过期，导致大量请求瞬间穿透到数据库，把数据库压垮。核心解决的思路就是**避免高频key过期时，大量请求同时访问数据库**解决方法有：**热点key永不过期**，**逻辑过期**，**互斥锁**。讲述时一定体现自己技术选型的思路。
- **缓存雪崩**：第一种，大量缓存key设置相同的过期时间，时间一到，key同时消失打到数据库。第二种，Redis集群出现故障，缓存层整体不可用。核心思路就是：**避免大量key同时过期**和**保存缓存集群高可用**，解决方案：**过期时间错开**、**缓存集群高可用方案**、**降级熔断策略**、**缓存预热**

到这先回顾一下我们解决缓存的什么问题了：存储在哪，同步策略，存储上限，redis三件套，大家是否都清楚了？对于某些概念不清晰的同学建议先对了解概念再来看这些话，最好是能有逻辑的梳理出来，那样就真正理解了。

接下来再补充一些常见问题：
- **Redis的持久化怎么做**：大部分人都能想到RDB和AOF，生产环境里一般是两者结合的方式，为什么呢？
- **Redis集群的数据分片与扩容**：我们之前讲过，Redis集群是多节点部署，那么海量数据怎么分配到各个节点呢？这就涉及到**数据分片策略**，大多都是用**一致性哈希**，去了解一下。
- **Redis的并发竞争问题**：高并发场景下，多个请求同时操作同一个Redis key，会出现并发竞争，秒杀项目中就是超卖问题。我们一般是使用分布式锁，基于redis/基于Redisson，保证同一时间只有一个请求能操作该key，或者使用Lua脚本锁定原子操作，避免并发修改导致的数据不一致。请结合你们自己的项目思考方案的技术选型，我这里仅列举常见的方案。
- **Redis的网络延迟问题**：Redis是分布式缓存，应用服务器和Redis集群之间通过网络通信的，如果网络延迟过高，会导致缓存查询的响应时间更长。由于网络分区问题，还可能会导致**脑裂问题**。所以最好将Redis集群 部署和应用服务器放在同一个机房，减少网络延迟；同时优化Redis的配置（比如调整TCP连接参数或者设置连接池）避免网络拥堵；对于高频访问的key，还可以在应用本地做一层二级缓存，比如java的Caffeine，减少Redis的网络请求。

**总结一下**：在分析Mysql和Redis的时候，可以从数据一致性，持久化，高可用性，并发竞争还有网络延迟等问题来分析，希望当你碰到这些词，脑海里立马能反映出来这些问题反应的是什么情况，对应的解决办法是什么。

在实际的业务中，在大厂的实际业务中，MySQl+Redis虽然能支撑基础的增删改查，但是面对海量数据的复杂检索、全文搜索、聚合统计场景，就有点力不从心了。咱们按照 **为什么需要 ES→ES 核心原理→请求如何落到 ES→ES 的问题与解决方案** 的逻辑来进行梳理。先叠甲一下，这方面平时面试考察的比较少，所以我的理解有可能比较浅，或者比较没那么有逻辑性，希望大家多多见谅。

接下来罗列三个痛点：

- **like的查询性能炸裂，无法支持高并发**：假如你的平台有100万数据，用户搜索“xx手机”，如果Mysql 的Select * from goods where name like '% 苹果手机'：。like '%关键词' 是最左匹配原则的失效场景，Mysql会走全表扫描，100万数据遍历下来，响应时间可能超过1秒，用户体验极差。同时无法做到**分词**，用户搜“苹果”搜不到“苹果手机”。而且如果用户想进行一些筛选，比如价格在5000-8000，内存256G等多条件查询，单靠Mysql查询效率会进一步下降，而且无法快速统计“各品牌手机效率”
- **海量数据的存储与检索能力不足**：MySQL是关系型数据库，数据都存磁盘（我们已经了解），当数据量达到千万级、亿级，单表性能会急剧下降。有些同学可能会想说**分库分表**来解决，虽然说这种方案能解决存储问题，但跨分片的复杂检索几乎是噩梦，你想要跨分片统计“全国各地区二手手机销量”，Mysql几乎无法在合理时间内完成。
- **不支持实时数据同步与搜索**：mysql主从复制有延迟还记得吗，比如用户刚发步一个商品，想马上搜索到，mysql无法做到秒级的检索支持，但ES天生支持近**实时搜索（NRT）**。

而ES刚好能解决这三个痛点！ES的核心价值就是用**倒排索引**解决海量数据的**全文检索、复杂聚合、实时搜索问题**，这是Mysql无法替代的，也是架构演进中必然要引入的中间件。

我自己对**倒排索引**的理解是，由“词”去找“文档片段”，有点想关键词检索的味道。传统的查找是通过”文档“去对应”词“。举个例子，还是搜苹果手机，ES会先将搜索词拆分为“苹果”“手机”两个关键词，然后再倒排索引中找到这两个关键词对应的文档，重合的就返回。这样就无需全表扫描了，直接通过**关键词**定位数据。

其次，ES它是天生的分布式架构，单台服务器无法存储海量数据，所以它会将索引拆成多个分片，分散不同节点：
- **主分片**：负责数据写入和查询，一个索引默认五个主分片
- **副本分片**：主分片的备份，负责高可用和负载均衡。一个主分片默认1个副本分片，数据会同步到副本分片。

最后再介绍一下**近实时搜索**与文档模型，数据写入ES后，回先写入内存缓冲区，然后每隔1秒执行refresh操作，将内存写入OS Cache，这个过程就是近实时的。

原理介绍完了，咱们回到请求链路，把 ES 融入到之前的 “请求 - MQ-MySQL- Redis” 架构中，讲清楚数据如何写入 ES、搜索请求如何处理。

- 用户写入Mysql，但为了能被ES搜索，我们需要**同步数据到ES**，这边就介绍最常用的方案：**MQ+Binlog**同步方案。用户发布商品——应用服务器校验——写入Mysql主库——mysql写入成功，向MQ发送一条商品新增消息——一个独立的ES同步伏虎，监听到MQ的商品消息，调用ES客户端，将数据写入ES。这样即使ES党积了，消息也会在MQ中积压，同步服务重启后可以继续消费，不会丢失数据，达到**解耦**的效果

![数据写入流程](/images/java-backend/scenarios/7.png)

- 用户搜索请求，也不会直接打到ES。比如还是输入搜索关键词“苹果手机”——应用服务器接受——应用服务器做请求校验——校验成功，调用ES客户端，向ES集群发送搜索请求——ES利用倒排索引快速检索，返回结果——应用服务器对ES返回的结果进行二次处理。注意，高并发场景下，ES搜索结果也可以缓存到**Redis**中

![搜索流程](/images/java-backend/scenarios/8.png)

ES当然那也不是完美的，也会存在很多问题，这边提出来供大家自查，但是确实面试下来考到比较少：
- **集群脑裂**：ES集群也是网络分区的，网络故障的话，每个小集群都认为自己是主集群，那就惨了。
- **写入有性能瓶颈、数据写入慢**：高并发写入数据，ES写入速度更不上啊，导致MQ消息挤压，也很麻烦的。
- **复杂的布尔查询、聚合统计导致搜索超时**
- **OOM，节点宕积**：ES是基于JVM的，堆内存如果设置不合理，会导致内存耗尽。
