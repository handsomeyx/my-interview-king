# 接入和路由层

## 概述

首先，我们先来还原一下用户在浏览器输入 URL 后发生的真实场景：

我们拿万能的URL www.baidu.com 举例开始，用户输入后，浏览器会先查缓存，看最近是否有没有访问过，有直接拿IP,没有直接发给本地DNS服务器（或者发给运营商DNS，电信，联通，移动等）如果你是电信网，就发给电信LocalDNS，最终能将www.baidu.com → 180.101.50.242（这个IP是CDN节点的IP哦，不是你家服务器的IP），接着CDN会判断资源的类型，看是**静态资源还是动态资源**。静态资源呢我们就就近缓存响应，动态资源比如说我们需要实时查询的订单数，CDN通过路由优化和持久连接技术进行加速转发给你的源站（也就是你运行后端代码的服务器）。

到这里还好吧。接着就是客户端和服务端要开始正式建立连接啦，通过TCP三次握手协议建立起了连接，相当于就是客户端和服务端中间修了个管道，传数据必须从管道中运行，但TCP是明文传输的，所以不太安全，为了防止**DDos或者中间人攻击**，我们必须用TLS握手给管道加锁，保证安全性。连接确认后，我们就可以用https去进行加密传输啦。
	
  但是，客户端能直接和服务端建立连接吗？www.baidu.com 每秒百万级QPS， 一台服务器的 CPU、带宽、连接数上限，连零头都扛不住。这可不是办法呀，怎么办呢？提高服务器的配置？肯定受很大限制的。那是不是可以将请求分担到其他的服务器？这就诞生了**负载均衡**这个概念了，我们的请求进来不直接到服务器上，而是先到负载均衡的中间件上面，由中间件进行转发给多个后端服务站里，这样即使某个服务器挂了，负载均衡中间件仍旧可以将请求发送给健康的服务器，用户请求仍旧被接受。
	
  好的，当请求被分发到服务器中，进入到我们的API网关层，还是那个老问题，即使负载均衡流量了，但是流量仍旧超过API网关所能承担的体量，这时候怎么办？这时候已经不能再分担压力了吧，所以我们要对**流量进行限制**。同时，这么多的流量请求，怎么区分请求呢？哪些请求是可以到我这个服务的，哪些是不可以的？是不是还得对请求进行一个身份**鉴权**的操作呀。另外网关层面要是被攻击导致接口不可用了怎么办，怎么维护服务的高可用性？是不是得**熔断保护**呀。所以在业务网关层面我们得先做到三个功能内容：身份鉴权，流量限流，熔断保护。进行完智慧，我们会根据请求的URL路由规则匹配到我们的微服务接口，找到对应的方法。

至此，以上就是接入和路由层面的全流程了。全流程我通过图方便大家更清晰的记忆。

#### 1.假设我们的平台正在进行一场突发的抢购活动，短时间内某一个地区的访问量超出了该地区 **CDN 节点** 的承载能力。此时，如果 CDN 节点响应变慢甚至宕机，系统应该如何通过 **DNS 调度** 实现自动灾备？如果 DNS 解析的结果被运营商强行缓存（DNS 劫持或污染），导致用户无法获取最新的 IP 结果，你有哪些方案可以绕过运营商的 DNS 限制？
<details>
<summary>点击查看答案</summary>
	分析一下，突发的抢购活动==瞬时大流量。CDN节点承载能力受节点硬件配置（CPU，内存等），出口带宽，网络质量和链路，单机并发连接数，节点调度策略等。DNS调度=一个智能的DNS解析助手，根据用户的地址，合适的运营商，CDN节点的负载程度来判断IP落在那个CDN节点是最优的选择。

对于场景题，你的回答一定要从应急情况和有优化时间的情况两种来讨论：

对于所有应急的情况都是想着能不能限制流量大小，或者短时间拉高CDN节点承载能力。有优化时间我们就可以去定位瓶颈的原因，针对这个抢购瞬时大流量，CDN有两个“硬伤”，一个是连接数，请求太多了，排队阻塞。一个是带宽受限制了。那DNS调度就是通过判断DNS节点的健康状况，当它发现某地区节点快被流量压垮了，会转移流量请求到哪些空闲的节点或者备用机房实现自动灾备。

但最头疼的是，有些运营商会搞DNS 劫持（给你返回广告IP）和DNS污染（直接伪造DNS响应）。为了绕过运营商的DNS限制，最成成熟的方案是 HttpDNS。它的逻辑很简单：不走运营商的DNS,能根据用户真实IP分配最近的CDN节点，最优机房。这样不仅能绕过运营商的乱指路，还能让官方根据你的真实位置，给你分配一个压力最小、离你最近的入口，彻底避开那些已经堵死的老路。
</details>


#### 2.在极端高并发下，服务器的 CPU 使用率飙升。我们知道 **HTTPS 的 TLS 握手** 涉及复杂的非对称加密计算，非常消耗 CPU。如果此时有大量新连接涌入，导致 CPU 过载，握手耗时从几十毫秒增加到几秒，你会如何优化这一层？
<details>
<summary>点击查看答案</summary>
首先，在极端高并发下，CPU 的使用率主要受三方面影响：一是海量的 TCP 连接维护（像是在门口排的长队）；二是密集的上下文切换（办事员在不同的窗口间来回切换）；三是最沉重的负担——TLS 握手时的非对称加密计算。

每一个 HTTPS 的新连接，在开始传输数据前，都要进行 TLS 握手。这个过程就像是为了确认身份，服务器得现场解密。如果一秒钟涌入几万个新连接，CPU 所有的算力都去解密了，自然就会过载，导致握手耗时从毫秒级直接卡到秒级。

通俗点说，TLS 握手最吃力的地方在于非对称加密。这就像是服务器要生成一对“母子钥匙”，计算过程涉及大量的模幂运算。虽然对称加密（传输数据时用的）也消耗 CPU，但它的效率极高，而非对称加密（握手确认身份时用的）效率极低。前者相当于你在流水线上切菜，后者相当于你需要雕刻一个亚里士多德人像。
	
而我们的优化思路其实就是两招：
会话复用（实际上就是少算几次非对称加密），两个核心方法：
- 1.Session ID/Ticket：只要亮出这张ID，服务器认出你是老熟人，直接跳过复杂的数学计算，一拍即合开始传数据。这能显著降低 CPU 的开销。
- 2.Keep-Alive（长连接）：尽量让一个连接多传点东西，别用一次就挂断，减少重新握手的次数。
找人帮算（计算卸载与算法优化）：

选更好的硬件或算法：
- 硬件加速卡（SSL Offset）：买专门的硬件（如 QAT 加速卡）把脏活累活从 CPU 身上卸下来，让专业的芯片去干。

- 更换算法（ECC 换 RSA）：就像是把复杂的圆周率计算换成更精简的公式。用 ECC（椭圆曲线加密） 代替传统的 RSA，可以在保证相同安全强度的前提下，让计算量大幅下降，从而保护 CPU。
</details>


#### 3.nginx中你部署了多个服务站， 如果其中一台后端服务器因为硬件故障突然响应极慢（但没挂死），而 Nginx 依然按照传统的 **轮询 (Round Robin)** 算法给它分发流量，这会导致什么后果？在 Nginx 中，有什么更智能的 **流量分发算法** 可以解决这种“慢服务器”问题？
<details>
<summary>点击查看答案</summary>
回顾一下负载均衡常见算法和使用场景吧：

-  轮询：请求按顺序轮流给服务器，所有服务器配置、性能差不多，没有长连接时可用
- 加权轮询：权重越高分越多请求，一般机器配置越高，想多抗流量
- 最少连接：分配给活跃连接数最少的服务器。长连接场景适用
- IP哈希：对客户端Ip做哈希，固定IP永远落在同一台机器，适用会话保持，同时能防刷单
- 随机算法：随机选一台，数量多，流量大使用，不追求绝对均衡
- 最短响应时间：优先分给响应最快、延迟最低的机器，对访问速度敏感。
- 一致性哈希：用哈希环，增减节点只影响少量的数据，缓存集群，需要尽量避免缓存雪崩的场景

![负载均衡常见算法](/images/java-backend/scenarios/3.jpg)


回到场景里，如果使用普通轮询算法，即使某台后端服务器响应极慢，Nginx 仍然会按顺序继续向它分发请求。这会导致大量请求在这台慢节点上阻塞，整体接口耗时飙升、大量超时，甚至引发雪崩，影响整个服务可用性。

我们可以用最短响应时间算法来解决这类慢节点问题。它会根据服务器的平均响应时间、活跃连接数综合判断，自动把流量更多转发给响应快、负载低的服务器，避开响应慢的节点，从而避免慢服务器拖垮整体业务。
</details>


#### 4.观察到你的网关有 **流量限流** 功能。如果某个微服务（比如“订单服务”）已经过载，网关触发了限流，但此时该服务依然收到了大量无效的重试请求，导致网关本身也变得响应缓慢。在这种情况下，**熔断保护 (Circuit Breaking)** 和 **限流 (Rate Limiting)** 的配置策略应该如何协同工作，才能防止“雪崩效应”波及整个网关层？
<details>
<summary>点击查看答案</summary>
回顾一下常见的限流算法吧：

- 漏铜:先往桶里塞请求，对桶本身开个口子，口子大小决定请求流出的快慢。适合削峰填谷，
- 令牌桶:桶里面装令牌，每个请求必须拿到令牌才有权利访问接口，所以令牌数和桶容量是关键。适合大流量
- 滑动窗口:窗口会随时间移动，只记录时间段的
- 固定窗口:固定时间段记录请求频数，但会存在突刺的情况。
