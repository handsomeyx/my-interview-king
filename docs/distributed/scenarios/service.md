# 业务逻辑与处理层场景题

> 分布式全链路场景题的**中间层**——接入路由（[gateway](./gateway)）把请求接进来，存储异步（[storage](./storage)）把数据落下去，**业务逻辑层负责"算"**：幂等、锁、事务、长任务、一致性。这一层是面试场景题的重灾区，因为它离业务最近、坑最密。

每题按「场景 → 核心矛盾 → 方案 → 取舍 → 易错点」展开，不是背八股，是练"拿到场景怎么拆"。

---

## 场景 1：如何设计接口幂等？

**场景**：用户狂点"提交订单"，或网络重试，同一笔请求被发多次。如何保证下单只下一次？

**核心矛盾**：网络不可靠 + 用户行为不可控 → 重复请求不可避免 → 业务必须能识别"这是同一个"。

**方案**（按强度）：
1. **唯一索引兜底**（最稳）：订单表对 `(user_id, biz_id)` 建唯一索引，重复插入抛异常，业务捕获转"已处理"。
2. **Token 机制**：前端先请求拿 token，提交时带 token，后端 `Redis SETNX` 处理一次后删除。防"重复提交"。
3. **状态机**：订单有状态（待支付/已支付/已取消），业务前置检查状态——只有"待支付"能走支付，重复请求直接拦截。
4. **乐观锁版本号**：`UPDATE t SET status=1 WHERE id=? AND status=0`——条件更新，只有第一次成功。

**取舍**：资金/订单类**强幂等**用唯一索引 + 状态机双保险；普通接口用 token 或乐观锁即可。别一上来分布式锁（太重）。

**易错点**：`SELECT` 后再 `INSERT` 的写法**不幂等**——并发下两个请求都 SELECT 到"不存在"，然后都 INSERT。要么唯一索引兜底，要么把"检查 + 写"放进一个事务加行锁。

## 场景 2：分布式锁怎么实现？

**场景**：定时任务部署多实例，如何保证同一时刻只有一个实例执行？

**方案**：
- **Redis `SET key value NX PX 30000`**：带过期时间的互斥量。释放用 Lua 脚本（`GET` 比对 value 再 `DEL`，保证删的是自己的锁）。
- **Redisson**：封装好的分布式锁（看门狗续期、可重入、公平锁），生产推荐。
- **ZooKeeper / etcd**：临时顺序节点，CP 强一致，性能比 Redis 低。

**追问：Redlock 算法是什么？要不要用？**→ Redlock 是 Redis 作者提的多节点加锁（向 N 个独立 Redis 加锁，多数成功才算成功），防单点 Redis 主从切换丢锁。但**有学术争议**（Martin Kleppmann 指出时钟漂移会破坏正确性）。生产里更常见：单 Redis + Redisson 看门狗；强一致场景用 ZK/etcd。Redlock 实际用得不多。

**易错点**：
1. **锁过期 + 业务没执行完**：A 拿锁处理慢，锁过期，B 拿到锁，A 处理完把 B 的锁删了。解法：value 存唯一标识，释放用 Lua 比对；或 Redisson 看门狗自动续期。
2. **释放非原子**：先 `GET` 再 `DEL`，中间可能被别人改。**必须 Lua 原子化**。

> 限流的"令牌桶/漏桶"算法细节见 [算法 / 限流](/algorithm/04-system-algorithms/rate-limiting/)，业务层只是调用方。

## 场景 3：分布式事务怎么选？

**场景**：下单要扣库存（库存服务）+ 扣余额（账户服务）+ 加订单（订单服务），跨库跨服务，怎么保证一致？

**核心矛盾**：本地事务管不了跨服务，但又不能不一致。

**方案谱系**（从强一致到最终一致）：

| 方案 | 一致性 | 性能 | 复杂度 | 场景 |
|---|---|---|---|---|
| 2PC | 强 | 低 | 高 | 数据库层（XA），基本淘汰 |
| TCC（Try-Confirm-Cancel）| 强 | 中 | 高（写三套逻辑）| 资金、库存 |
| Saga | 最终 | 高 | 中（长事务）| 订单流程、跨多服务 |
| 本地消息表 | 最终 | 高 | 低 | 异步解耦（**最常用**）|
| 最大努力通知 | 最终 | 高 | 低 | 对账、第三方回调 |

**取舍**（高频面试点）：互联网大多数业务**不追求强一致**，用**本地消息表 / Saga + 补偿**即可。资金/库存这类才上 TCC。2PC 几乎不用（性能差、阻塞）。

**本地消息表原理**：业务表 + 消息表在**同一个库**，本地事务一起写（保证原子）；后台扫消息表发 MQ，消费方处理完 ACK，失败重试。这套把"跨服务事务"降级成"本地事务 + 异步重试"，是工程上最实用的方案。

**易错点**："用了 MQ 就有分布式事务"——错。MQ 默认 at-least-once，**消费端必须幂等**（见场景 1）。事务消息（RocketMQ）只是省了本地消息表，幂等仍要业务自己做。

## 场景 4：长任务怎么异步化？

**场景**：用户点"导出报表"，要查几百万行数据生成 Excel，同步处理 30 秒接口超时。怎么办？

**方案**：
1. 接口立即返回 taskId（202 Accepted），后台异步处理。
2. 任务状态写库（待处理/处理中/完成/失败）。
3. 处理完写对象存储（OSS/S3），状态置完成。
4. 通知用户：WebSocket 推送 / 站内信 / 前端轮询查状态。

**核心矛盾**：HTTP 不适合长连接等结果，必须解耦"提交"和"完成"。

**易错点**：异步任务的**状态机**一定要设计好——"失败可重试"、"重复提交不产生两份结果"（幂等）。很多人只想着异步化，忘了失败补偿和幂等，上线就炸。

**追问：定时任务 vs 消息队列，长任务用哪个？**→ 实时触发用 MQ（提交即触发）；批量触发用定时调度（XXL-JOB / elastic-job）。两者不冲突，复杂系统常组合使用。

## 场景 5：大事务 / 慢接口怎么优化？

**场景**：一个接口里 RPC 调了 5 个服务、查了 10 次库、还发了短信，整体 3 秒，怎么优化？

**排查顺序**（别上来就猜）：
1. **链路追踪**（SkyWalking / Zipkin）定位最慢的段。
2. **DB 慢查询**：索引、N+1、大表 scan。
3. **RPC 串行 → 并行**：5 个独立调用用 `CompletableFuture` 并行。
4. **异步化非核心**：短信、日志、统计扔 MQ 异步。
5. **缓存**：读多写少加缓存（注意一致性）。

**易错点**："大事务"特指**数据库事务里包了 RPC / 远程调用**——事务期间连接占用、行锁不释放，RPC 慢会拖垮连接池。**事务里只做 DB 操作，RPC 移出事务**。这是高频坑。

## 场景 6：业务层限流降级怎么做？

**场景**：秒杀/大促，接口扛不住，怎么保住核心？

**分层防御**（从外到内）：
1. **网关层限流**（见 [gateway](./gateway)）：Sentinel / Nginx 限流，挡在最前面。
2. **业务层熔断**：依赖服务挂了，快速失败而不是级联等待（Sentinel / Hystrix / Resilience4j）。
3. **降级**：非核心功能返回兜底（推荐列表挂了返回热门兜底）。
4. **排队削峰**：秒杀场景请求进 MQ，业务按消费能力处理。

**易错点**：熔断和降级**不是一回事**——**熔断**是"依赖挂了我快速失败保护自己"；**降级**是"主动放弃非核心保核心"。熔断是被动触发，降级是主动策略。面试常被混问。

> 限流算法（令牌桶/漏桶/滑动窗口）见 [算法 / 限流](/algorithm/04-system-algorithms/rate-limiting/)；负载均衡算法见 [算法 / 负载均衡](/algorithm/04-system-algorithms/load-balancing/)——算法原理在算法板块，业务层是调用方。

## 易错点速查表

| 场景 | 关键 |
|---|---|
| 幂等 | SELECT+INSERT 不幂等；唯一索引 / 状态机 / 乐观锁兜底 |
| 分布式锁 | 释放要 Lua 原子化；锁过期用看门狗续期；Redlock 有争议 |
| 分布式事务 | 大多数业务用本地消息表 / Saga；TCC 仅资金类；2PC 淘汰 |
| MQ + 事务 | 消费端必须幂等；事务消息仍要业务幂等 |
| 长任务 | 状态机 + 失败补偿 + 幂等，三者缺一 |
| 大事务 | 事务里只做 DB；RPC 移出事务（防连接池耗尽） |
| 熔断 vs 降级 | 熔断被动保护自己；降级主动弃非核心 |

> 业务逻辑层的核心是"**把场景拆成可解的子问题**"。看完这一层，回 [scenarios 总览](./) 看接入路由（gateway）和持久化异步（storage）怎么配合——三层拼起来就是一个完整的后端系统。
