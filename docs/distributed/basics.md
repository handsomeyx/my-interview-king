# 分布式基础

> 分布式理论的"地基"。核心四块：**CAP 取舍、BASE 最终一致、一致性哈希、共识算法（Raft/Paxos）**。很多八股停留在"CAP 是一致性/可用性/分区容错"的背诵，追问"三选二到底选谁、为什么"就答不上。本文按问答，每题答 + 追问 + 易错点。

## 思考锚点

单机系统中，所有数据存在一台机器上，操作系统帮你保证一致性。但在分布式系统中，数据存在多台机器上，网络可能延迟、丢包甚至断连——你不能再假设"所有节点同时看到相同的数据"。

这就是分布式的核心困境：**网络分区是必然的，你必须在「数据一致」和「服务可用」之间做取舍**。CAP 不是"三选二"的静态标签，而是在网络分区真的发生时，你必须决定是暂停服务（选 CP）还是接受不一致（选 AP）。

本文要讲清楚 CAP 的真实含义、BASE 最终一致的工程实现、一致性哈希解决什么问题，以及 Raft/Paxos 如何在多节点间达成共识。

## Q1：CAP 是什么？为什么三选二？

**答**：CAP 是分布式系统的三个性质：
- **C（Consistency，一致性）**：所有节点同一时刻看到同样的数据。
- **A（Availability，可用性）**：每个请求都能在合理时间内得到非错响应。
- **P（Partition tolerance，分区容错）**：网络分区（节点间通信断）时系统仍能工作。

**三选二**：网络分区（P）在真实分布式里**不可避免**，所以 P 必选。剩下只能在 C 和 A 之间选：
- 分区发生时**选 C**：拒绝不一致的读写（牺牲可用性 A）。
- 分区发生时**选 A**：允许各分区自己处理（牺牲一致性 C）。

**易错点**：CAP 不是"任何时候都三选二"，而是**"网络分区发生时"才在 C 和 A 间取舍**。没有分区时，可以同时有 CA。这是最高频的 CAP 误解。

> 🤔 停下来想想：没有网络分区时，CAP 三选二还成立吗？

## Q2：CP 和 AP 的代表系统？

**答**：
- **CP**（保一致性）：ZooKeeper、etcd、HBase、强一致数据库。分区时宁可拒绝服务，也不让数据不一致。
- **AP**（保可用性）：Eureka、Cassandra、DynamoDB。分区时各节点继续服务，事后靠最终一致修复。

**追问**：注册中心该选 CP 还是 AP？→ 一般**选 AP**（如 Eureka、Nacos AP 模式）。理由：注册中心短暂不一致（某实例列表晚几秒同步）业务能容忍（重试 + 熔断兜底）；但注册中心不可用 = 所有服务发现失败 = 全站挂。所以**可用性优先**。ZooKeeper（CP）当注册中心反而不理想——分区时它拒绝服务。

**易错点**：别死记"ZK 是 CP、Eureka 是 AP"，要能说清**为什么注册中心倾向 AP**——这是面试加分点。

## Q3：BASE 是什么？

**答**：BASE 是 CAP 中选 AP 后的实践指南：
- **B（Basically Available，基本可用）**：故障时允许损失部分可用性（响应变慢、降级、跳转兜底页）。
- **S（Soft state，软状态）**：允许中间状态存在（数据正在同步中，不算错）。
- **E（Eventually consistent，最终一致）**：不要求强一致，但保证一段时间后最终一致。

**与 CAP 的关系**：BASE 是 **AP + 最终一致**的工程化。互联网大多数高并发场景（电商、社交）都用 BASE——强一致代价太高（牺牲可用性和性能），最终一致 + 业务补偿足够。

**易错点**：BASE 不是"不保证一致"，是"不保证**强**一致，但保证**最终**一致"。两回事。

## Q4：一致性哈希解决什么问题？

**答**：分布式存储/缓存的**路由问题**——给定一个 key，应该存到哪个节点？

**朴素方案**：`hash(key) % N`（N 是节点数）。问题：**节点增减（N 变）时，几乎所有 key 都要重新映射**，缓存全失效、数据大迁移。

**一致性哈希**：把 hash 空间组织成一个**环**（0 ~ 2³²-1）。节点和 key 都映射到环上，**key 顺时针找到的第一个节点就是它的归属**。节点增减只影响**环上相邻一段**的 key（不是全部），大幅减少迁移。

**易错点**：朴素一致性哈希有**数据倾斜**问题——节点可能扎堆在环某段。解法是**虚拟节点**：每个真实节点映射到环上多个虚拟点（如 150 个），让分布均匀。**生产实现一定要配虚拟节点**，不配基本一定倾斜。

> 一致性哈希的算法细节（环、虚拟节点、哈希函数选择）见 [算法 / 一致性哈希](/algorithm/04-system-algorithms/consistent-hashing)——后端场景和算法原理两边对照看，是本站独有的网状结构。

## Q5：Raft 怎么工作的？

**答**：Raft 是共识算法（让多个节点对一个值达成一致），比 Paxos 好懂。拆成三个子问题：

1. **Leader 选举**：节点有三种角色——Follower / Candidate / Leader。Leader 挂了，Follower 超时变 Candidate，拉票获多数票当选新 Leader。`term`（任期）做版本号，防止旧 Leader 干扰。
2. **日志复制**：客户端请求只发给 Leader，Leader 写本地日志后**并发复制到所有 Follower**，**多数 Follower 确认后提交**（commit），返回客户端成功。
3. **安全性**：保证已提交的日志不被覆盖（选举约束：只有日志"最新"的 Candidate 能当选）。

**关键**：Raft 是**多数派（Quorum）**——只要多数节点活着就能工作。3 节点容忍 1 个故障，5 节点容忍 2 个。

**追问**：为什么共识算法都要多数派？→ 多数派 + 「任意两个多数派必有交集」→ 已提交的值不会被新多数派推翻，一致性得证。

> 🤔 停下来想想：为什么多数派能保证一致性？任意两个多数派必有交集——这是为什么？

**易错点**：Raft 的 commit 指的是**多数节点持久化**，不是"所有节点"。少数慢节点落后不影响 Leader 推进，它后续慢慢追上。

## Q6：Raft 和 Paxos 区别？

**答**：
- **Paxos**：理论基础（Basic Paxos / Multi-Paxos），严谨但**难懂难实现**。
- **Raft**：为"可理解性"设计的算法，功能等价于 Multi-Paxos，工程实现多（etcd、Consul、Nacos）。

**易错点**：别答"Paxos 落后"——Paxos 是**理论奠基**，Raft 是**工程友好**的实现。它们解决同一类问题（共识），Raft 的设计目标就是"做到 Paxos 的事但好懂"。ZAB 是 ZooKeeper 自己的共识协议，类似 Raft 但强调顺序保证（主备同步顺序）。

## 易错点速查表

| 知识点 | 关键 |
|---|---|
| CAP | 分区**发生时**才在 C/A 间选；P 必选；无分区时可有 CA |
| 注册中心 | 倾向 AP（可用性优先）；ZK(CP) 当注册中心不理想 |
| BASE | 最终一致，不是"不保证一致" |
| 一致性哈希 | 解 `%N` 增减节点全量迁移；虚拟节点解倾斜，生产必配 |
| Raft commit | 多数节点持久化即提交，不是所有节点 |
| 多数派 | 容忍 (n-1)/2 个故障；3 容忍 1，5 容忍 2 |
| Raft vs Paxos | 同一类问题，Raft 工程可理解，Paxos 理论奠基 |
