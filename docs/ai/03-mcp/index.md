# MCP，通信协议与上下文管理

前两章节梳理了Agent的架构和组件，道了 Agent 如何自主思考、自主执行任务。但 Agent 并不是孤立存在的——它需要和 LLM 沟通、和其他 Agent 协作，还需要记住交互过程中的关键信息，而这一切的核心支撑，就是 **MCP 协议**及相关技术。

## MCP基础
MCP（Model Context Protocol，模型上下文协议）它就像 AI 世界里的“普通话”，规范了 Agent 与 LLM、Agent 与 Agent 之间的通信方式，确保它们能“互相听懂、高效协作”。

### MCP协议要解决什么问题？
- 解决**沟通混乱**：没有统一协议时，Agent 与 LLM、Agent 与 Agent 可能采用不同的信息格式，导致“鸡同鸭讲”（比如 A Agent 用 JSON 格式传递信息，B Agent 用文本格式，无法识别）；
- 解决**上下文丢失**：确保 Agent 与 LLM 交互时，能完整传递上下文信息（比如用户之前的需求、Agent 之前的执行步骤），让 LLM 能“记住”之前的内容；
- 解决**多主体协同**：为多 Agent 协作、多模态交互提供统一的通信标准，让不同类型的 Agent（比如文本 Agent、语音 Agent）能高效协同。

补充：MCP 协议的核心优势是“通用性”和“可扩展性”——它不依赖特定的 LLM 或 Agent 框架，无论是 GPT、文心一言，还是 LangChain、MetaGPT 框架，都能适配 MCP 协议，同时支持后续新增功能。

### MCP架构
架构包含以下核心组件：
- **消息中枢**：负责路由和分发指令，kafka这类的MQ做命令总线，所有控制指令通过Topic广播，消费者按需订阅，实现解耦
- **控制单元**：接受到消息后执行具体逻辑，不直接暴露HTTP接口，而是被动相应事件
-  **状态反馈器**：反向上报执行结果，形成闭环。通常往一个集中式存储写状态

### MCP 协议如何工作
核心是“统一信息格式+上下文传递+交互闭环”，我们用一个简单的案例（Agent 与 LLM 交互）就能理解完整流程：
1. **信息封装**：Agent 将需要传递的信息（比如用户需求“帮我查明天的天气”），按照 MCP 协议规定的格式进行封装——比如封装成“类型（需求）+ 内容（查明天天气）+ 上下文（无历史交互）+ 参数（城市：北京）”的结构；
2. **信息传递**：Agent 通过通信通道（比如 API、消息队列），将封装好的信息传递给 LLM；
3. **信息解析**：LLM 按照 MCP 协议的规范，解析 Agent 传递的信息，明确需求、上下文和参数；
4. **结果反馈**：LLM 执行需求（查询天气），将结果按照 MCP 协议格式封装，反馈给 Agent；
5. **上下文更新**：Agent 接收反馈结果，将“需求+结果”更新到上下文，为后续交互（比如用户追问“后天呢”）做准备。

核心技术细节：MCP 协议的核心是“上下文标识符”和“信息类型定义”——每个交互都有唯一的上下文标识符，确保 LLM 能对应到正确的交互会话；同时定义了多种信息类型（需求、指令、结果、错误提示），让接收方能快速识别信息用途。

### 如何落地协议开发呢？

- **实现方法**：
  - 基于**现有框架适配**：主流 Agent 框架（LangChain、MetaGPT、Dify）都已支持 MCP 协议，只需在框架中配置 MCP 协议参数（比如信息格式、通信方式），即可实现协议对接；
  - **自定义实现**（简单场景）：如果是简单的 Agent 系统，可自定义 MCP 协议的核心格式（比如用 JSON 格式定义信息结构），确保 Agent 与 LLM、Agent 之间能按照该格式传递信息。

- **最佳实践**：
  - 统一**信息格式**：无论 Agent 与 LLM、Agent 与 Agent 如何交互，都严格遵循 MCP 协议规定的格式（比如统一用 JSON 格式，包含类型、内容、上下文、参数四大字段）；
  - **保留上下文标识符**：每个交互会话都分配唯一的上下文标识符，避免上下文混淆（比如用户 A 和用户 B 同时使用 Agent，通过标识符区分两者的交互上下文）；
  - **错误处理**：在协议中定义明确的错误提示格式（比如“错误类型+错误原因+解决方案”），当交互出现错误时（比如工具调用失败），能快速定位问题。



### MCP支持的两种交互模式

- **请求响应**：客户端发请求，携带上下文，服务端完全基于上下文生成响应。类似HTTP，适合一次性任务
- **会话**：维护一个持续的上下文会话状态，客户端可以连续发送多条消息。每条都基于之前的对话历史进行理解与回应，场景就是聊天机器人。看业务需不需要记住前面的内容。

### MCP的开发模式

- **stdio，本地进程通信**：本地进程间直连，MCP默认，最简单的开发/调试模式
- **SSE模式，网络通信**：远程的标准长连接模式，支持多客户端，流式推送

### MCP的安全协议
- 传输安全靠TLS/SSl加密
- 身份认证走双向证书，APIkey或令牌，确定双方都是合法的
- 数据层面防敏感信息裸奔，在payload内部做字段加密，就是支付类的卡号
- 审计和日志也得更上，关键操作记录请求来源，避免出事，还可以追溯
## 上下文管理
在上一部分 Agent 组件的学习中，我们了解过记忆组件，而上下文管理，就是“记忆组件的核心工作”——它负责管理 Agent 交互过程中的上下文信息。

### 上下文表示
上下文表示，就是“用什么格式、什么结构存储上下文信息”，核心是“清晰、可检索、可更新”，我们重点掌握2种常用的表示方法：
- **结构化表示**（最常用）：用固定的结构（比如 JSON、字典）存储上下文，明确每个字段的含义，方便 Agent 和 LLM 快速解析和检索——比如：
        {
  "context_id": "会话123",  // 上下文标识符
  "user需求": "帮我查明天北京的天气",
  "agent行动": "调用天气API查询",
  "反馈结果": "明天北京晴，气温10-20℃",
  "时间戳": "2026-04-04 10:00"
}
- **非结构化表示**：用纯文本格式存储上下文，适合简单场景（比如短对话）——比如“用户：帮我查明天北京的天气；Agent：已调用天气API；结果：明天北京晴，气温10-20℃”；

### 上下文更新：
Agent 的交互是一个持续的过程，上下文也需要动态更新，在交互过程中，不断添加新的信息、更新任务状态，确保上下文能反映最新的交互情况。核心遵循“新增+更新+清理”的逻辑：
- **新增信息**：每次交互（用户输入、Agent 行动、反馈结果）后，都将相关信息添加到上下文——比如用户追问“后天呢”，就将“用户需求：查后天北京天气”新增到上下文；
- ** 更新状态**：当任务执行状态变化时（比如从“未执行”到“已执行”，从“执行中”到“执行失败”），更新上下文的任务状态——比如 Agent 调用天气API失败，就将“agent行动状态”更新为“调用失败”；
- **清理过期信息**：对于过期的上下文（比如会话结束、任务完成），及时清理，避免占用过多资源——比如用户结束对话后，清理该会话的上下文信息，只保留长期有用的记忆（比如用户喜好）。

### 上下文优化：
如果上下文信息过多、过于杂乱，会导致 Agent 和 LLM 解析缓慢、检索困难，影响交互效率——上下文优化，就是“精简上下文、提升检索效率”，我们需要掌握3个核心技巧：
- **上下文压缩**：将冗长的上下文信息进行压缩，保留核心内容（比如只保留用户需求、关键行动和结果，删除无关细节）——比如将“用户说‘我想查一下明天北京的天气，因为我要去北京出差，需要准备衣服’”压缩为“用户需求：查明天北京天气（出差备用）”；
- **关键词索引**：为上下文添加**关键词索引**（比如“天气、北京、明天”），让 Agent 和 LLM 能快速检索到相关上下文——比如用户问“北京天气”，能通过关键词快速找到之前的天气查询上下文；
- **上下文分层**：将上下文分为“短期上下文”（当前会话的临时信息）和“长期上下文”（用户喜好、历史经验），分层管理——短期上下文优先处理，长期上下文按需检索，提升效率。

## 多Agent之间的通信

常见的Agent间的通信的协议有以下3种：

- **MCP 协议（核心）**：作为 Agent 间通信的基础协议，规范了上下文传递、任务指令、结果反馈等核心信息的传递格式，确保不同 Agent 之间能互相理解；
- **RPC 协议（实时通信专用）**：适合**实时性**要求高的 Agent 间通信（比如两个 Agent 协同处理用户问题，需要实时同步信息），能实现 Agent 之间的直接接口调用，传递信息速度快；
- **消息队列协议（异步通信专用）**：适合异步通信场景（比如主 Agent 分配任务后，从 Agent 执行完成后再反馈结果），通过消息队列传递信息，避免 Agent 之间直接耦合，提升系统稳定性。


### 消息格式

多Agent 之间传递的消息，需要有统一的格式，才能确保接收方能快速解析信息。消息格式基于 MCP 协议规范，核心包含4个字段：
- **发送方标识**：明确发送消息的 Agent 是谁（比如“Agent1-物料采购”）；
- **接收方标识**：明确接收消息的 Agent 是谁（比如“Agent2-场地预订”）；
- **消息类型**：明确消息的用途（比如“任务分配、结果反馈、错误提示”）；
- **消息内容**：具体的消息信息（比如任务分配的内容、参数、截止时间）。

eg: {
  "发送方": "主Agent-活动策划",
  "接收方": "从Agent-物料采购",
  "消息类型": "任务分配",
  "消息内容": {
    "任务": "采购活动物料",
    "参数": {
      "物料名称": "气球、横幅、鲜花",
      "数量": "气球100个、横幅5条、鲜花20束",
      "截止时间": "2026-04-10"
    },
    "上下文标识": "活动策划-会话456"
  }
}

### 通信安全：

Agent 之间传递的信息，可能包含敏感内容，所以有必要对通信进行一个安全性的防护：

- **消息加密**：对 Agent 之间传递的消息进行加密（比如用 AES 加密算法），即使消息被拦截，也无法被破解；
- **身份认证**：Agent 发送消息前，需要验证接收方的身份（比如通过密钥认证），避免恶意 Agent 冒充接收方接收消息；
- **消息校验**：接收方收到消息后，校验消息的完整性（比如校验消息的哈希值），确认消息没有被篡改——如果消息被篡改，哈希值会发生变化，接收方会拒绝处理该消息。

2.现在有个问题 ，一个agent有很多mcp工具可以选择，但是需求过来了以后，并没有匹配到我想要的那个mcp，怎么解决？
<details>
<summary>点击查看答案</summary>
答：先要知道根本原因：
- 工具描述Tool Desciption不够精确，LLM 是靠描述判断要不要调用，写得模糊就会选错 / 漏选。
- 意图理解不足，用户需求太泛、隐含意图多，LLM 没理解真正要做什么。
- 工具太多选择困难，工具列表过长，LLM 注意力分散，出现 “选择瘫痪”。
- 路由逻辑太差，完全靠 LLM 自由判断，没有规则、分类、召回增强。
- 参数不足：没有给 Few-shot 示范 “什么场景用什么工具”。

所以我们基本上就是从原因去得到解决方法：
-优化工具描述：功能是什么，什么时候用，什么时候不用，输入参数含义。
-工具分类+两层路由：第一层：意图分类器，属于哪一大类，在我项目就是树形意图，第二层：只在该类别下筛选少量候选工具，不让LLM从几十上百个里盲选。
- 增加工具检索机制 ：把所有MCP工具向量化，用户问题进来，检索top3-5最相关工具。
- 强化prompt。
- 微调/对齐小模型：收集错误的bad case，用SFT和DPO去微调去优化。
</details>

4.agent调用mcp的整体流程是怎样的，最后又是怎么返回给用户的？
<details>
<summary>点击查看答案</summary>
答：
1. 用户发起请求，agent接受任务，判断是否调用外部工具，进入ReAct循环。
2. 想MCP Server发送tools请求，查询可用列表。决定一下调用哪一个。
3. agent生产MCP调用指令，生成结构化调用参数
4. 传输层发送指令到MCPServer，它执行工具逻辑，解析JSON找到工具实现，实现具体业务逻辑，收集执行结果
5. MCP Service返回结果给Agent，将结果封装成JSON+RPC响应。
6. Agent整合救国，生成最终答案。
7. 返回给用户

</details>
