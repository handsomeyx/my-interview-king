# 核心本体

## 思考锚点

如果说 LLM 是 Agent 的「大脑」，那么 Agent 的架构就是「**让大脑能指挥身体干活的整套系统**」。

Agent 的核心架构可以用「输入 → 处理 → 输出」闭环来理解，但真正的难点在于「处理」环节——它需要多个组件协同工作：感知组件负责理解用户输入、大脑组件（LLM）负责思考决策、规划组件负责拆解任务、行动组件负责调用工具、记忆组件负责记住上下文。

这五个组件不是随意堆砌的，而是围绕「**目标导向**」的核心原则设计的——每个组件都服务于让 Agent 更好地完成用户目标。

在学习完LLM之后，我们需要将学习聚焦于AI Agent本身，重点理解"组件的作用""架构的逻辑""协作的方式"。

## Agent的架构

这小节我们需要学习Agent 由哪些部分组成、各部分如何分工、如何协同工作，决定了 Agent 的"行动能力"和"灵活度"。Agent的**基本架构核心**是"**输入→处理→输出**"的闭环：**用户需求（输入）→ 组件协同处理（结合 LLM 思考、调用工具）→ 任务结果（输出）**，同时通过**记忆组件**记录过程，形成持续优化的闭环。

### 架构设计原则
在此之前，我们也要了解一下Agent设计原则，方便你对自己做的项目进行一个定位：
- **目标导向**：架构设计围绕Agent的核心目标来展开的，比如你要做一个客服Agent的项目，目标是高效解决用户问题，那么你的架构就需要重点强化"推理组件"和"工具使用主键"，方便你快速理解用户需求。
- **组件解耦**：各个组件之间相互独立，互不干扰，比如"规划组件"负责制定计划，"记忆组件"负责存储信息，某个组件出问题，不会影响其他组件的正常工作。
- **可扩展性**：架构能灵活的添加新的组件或功能——比如你的客服Agent新增了"语音交互"功能，只需要添加一个"语言识别组件"，不用修改整个架构。

### Agent架构的五大组件
这小节我不举例来解释了，都很好理解。
- **感知组件**：获取环境/用户输入并结构化，接受并理解用户的输入。
- **大脑组件**：LLM，思考、负责决策、推理和规划。
- **规划组件**：把模糊的任务变成可执行化步骤，第一步干什么，第二步干什么，要不要循环，要不要重试。
- **行动组件**：输出、调用工具与环境互动，通常用MCP来保证调用格式规范，通常用Function Calling或者API来调用工具。
- **记忆组件**：对话管理，存在上下文窗口（context window）存储短期记忆，长期记忆靠向量数据库来实现。

### 主流的Agent架构有哪些？
目前已经创造出很多种基于各种目标的Agent架构，接下来我来一一介绍：
- **Plan-and-Execute（规划-执行架构）**：先完整规划处步骤列表——再一步步执行，执行中部轻易改计划。要特别**注意**，规划不准的话全程就会跑偏。
- **Reflexion（反思架构）**：执行——观察结果——自我反思、纠错——重新执行，相当与给Agent加了"复盘能力"，容错率高，能自我修正。但是轮次变多了，耗时变长
- **Self-Ask（自问自答架构）**:Agent把复杂问题拆成一连串的小问题，Agent它自己问直接，逐步搜索/推理得到答案，适合知识问答。
- **TOT（思维树）**：不只是一条线思考，而是像树一样分叉探索多条推理路径，择优选择。推理质量高，适合数学、逻辑等领域，但是极耗token，速度慢
- **GOT（思维图）**：把思路建成图结构，节点是想法，边是依赖，可合并、循环、跳转。表达能力极强，复杂推理天花板。工程实现复杂。
- **（RAG+Agent）**：Agent 每一步思考前，先检索外部知识，再决定做什么。知识新、不易幻觉。但是检索不准回拖累整个流程。



## 多Agent
### 协作模式
不同的复杂任务，需要不同的协作模式，小白重点掌握3种主流协作模式，结合场景理解：

- **主从模式**（最常用）：有一个"主 Agent"（负责整体规划、任务分配），多个"从 Agent"（负责执行具体任务）——比如年度活动策划，主 Agent 制定整体方案，从 Agent 分别负责物料采购、人员安排、场地预订，主 Agent 同步协调各从 Agent 的进度；
- **平等协作模式**：多个 Agent 地位平等，各自负责一个领域，通过沟通同步信息、协同完成任务——比如 AI 客服系统，一个 Agent 负责解答订单问题，一个 Agent 负责解答售后问题，遇到跨领域问题，两个 Agent 相互沟通，共同给出答案；
- **层级协作模式**：多个 Agent 分为不同层级，上层 Agent 负责整体规划，下层 Agent 负责具体执行，层层递进——比如项目管理系统，上层 Agent 负责项目整体规划，中层 Agent 负责模块分工，下层 Agent 负责具体任务执行。

### 多Agent之间的沟通

多个 Agent 要协同工作，必须能"互相沟通"，通信机制就是多 Agent 之间的"沟通语言"，核心是"规范信息传递的格式和方式"，确保 Agent 之间能听懂彼此的信息——这和我们之前学的 MCP 协议密切相关。
- **核心通信方式**：
        
  - **消息队列通信（最常用）**：多个 Agent 通过**消息队列**（比如 RabbitMQ、Kafka）传递信息，Agent 发送消息到队列，其他 Agent 从队列中获取消息，避免直接耦合——比如主 Agent 把"物料采购任务"发送到队列，采购 Agent 从队列中获取任务并执行；

  - **RPC 通信**：Agent 之间**直接调用对方的接口**，传递信息，适合实时性要求高的场景——比如两个 Agent 协同处理用户问题，实时同步用户需求和处理进度；

- **通信协议**：主要基于 **MCP 协议**，规范信息传递的格式（比如任务信息、执行结果、错误提示），确保不同 Agent 之间能"互相理解"——比如 Agent A 发送"任务：采购物料，参数：物料名称、数量"，Agent B 能通过 MCP 协议，准确识别任务和参数。

### 多Agent的分工策略

核心是**合理分工**，将复杂任务拆分成多个子任务，分配给合适的Agent。

2种常见策略：
**基于能力分配**：根据每个 Agent 的擅长领域，分配对应的任务
**基于负载分配**：根据每个 Agent 的当前负载（是否在执行任务、执行任务的数量），分配任务

### 如何判断Agent的能力强弱

当我们开发出一个 AI Agent 后，如何判断它的能力强弱？是否能满足实际需求？这就需要通过**Agent 评估**，接下来我会介绍常见的**评估指标**和**评估方法**。

评估指标（这在简历中可以来体现你的Agent的能力）：
- **任务成功率**：Agent完成任务的比例（比如100个任务，成功完成85个，成功率就是85%）。
- **响应速度**：定义Agent从接受用户需求到输出任务结果的时间——时间的长短影响用户的体验
- **准确性**：Agent输出结果的正确程度。
- **灵活性**：Agent应对复杂需求、异常情况的能力，（比如用户需求变更、工具调用失败，Agent 是否能调整方案）。
- **资源消耗**：Agent运行过程中消耗的服务器资源（CPU，内存）。

评估方法（面试中问你如何测试的）：
-**人工评估**：：由人工模拟用户，向 Agent 发送需求，判断 Agent 的任务完成情况、输出准确性。比如人工发送100个客服问题，判断 Agent 回答的正确率、响应速度，适合小范围评估；
-**自动化评估**：通过代码编写测试用例，自动向 Agent 发送需求，自动统计评估指标。
-**用户反馈评估**：让实际用户使用 Agent，收集用户的反馈（比如满意度评分、问题反馈），间接评估 Agent 的能力。

#### 基准测试
就是用行业通用的测试数据集和方法，对比Agent与其他Agent的能力，判断Agent的行业水平。

-**常用的基准测试工具**：AgentBench（字节的）覆盖多场景的Agent测试），MTBench（大模型与Agent综合测试工具）。
-**测试方法**：将Agent接入基准测试工具，运行测试用例，工具会自动生成评估报告，对比Agent与其他模型/Agent的性能，帮我们找到优化方向。
