# 上下文管理 
这一章节重点梳理一下，在面试中，这章节是非常高频的考点。

你跟豆包聊天，先问“帮我整理一份 Excel 数据”，豆包回复“可以，请提供 Excel 文件或具体数据”；你接着说“文件是关于 2026 年第一季度的销售数据”，豆包能立刻衔接上，而不是问“你说的文件是什么”——这背后，就是**「上下文管理」**在发挥作用。

简单来说，AI Agent 的上下文管理，就是“**让 Agent 记住关键信息、用好关键信息**”的一套机制。LLM它本身是无状态的，所以它不知道上一句说了什么，所以所有的“记忆”都依赖我们通过上下文管理将历史信息、任务信息主动传递给它。

我们常用的豆包，GTP呀，本质上就是最简单的上下文管理，系统把你和模型的每一轮对话都存起俩，每次回复时，再把这些历史对话一起传给模型，确保对话能连贯。而AiAgent的上下文管理，比这复杂的多，他管理的不只是对话，还有**任务状态，工具交互，用户偏好**。

## 上下文管理是Agent的核心竞争力
举两个反面例子，帮大家理解它的重要性： 

1. 反面案例1：**上下文管理缺失**——你让 Agent 帮你规划“5天东京亲子游”，先要求“预算1.5万元”，接着补充“避开迪士尼”，结果 Agent 给出的方案里依然包含迪士尼，原因是它没记住你后续的补充要求，相当于“左耳进、右耳出”；
2. 反面案例2：**上下文管理混乱**——你让 Agent 开发一个简单的 Python 工具，先后提了“用 PEP8 规范”“包含注释”“支持批量处理”三个要求，Agent 只执行了最后一个，因为它被大量信息淹没，找不到关键约束，出现“Lost in the Middle”（关键信息被中间噪音覆盖）的问题。

所以做好上下文管理，要解决解决 AI Agent 的这些问题，也是它和普通问答机器人的本质区别：

1. 解决“**健忘**”问题：让 Agent 记住历史交互、任务目标、用户偏好，实现连贯决策（比如智能客服记住用户3个月前反映的问题，再次咨询时无需重复说明）；
2. 解决“**混乱**”问题：筛选无关信息，聚焦核心需求，避免信息过载导致的决策偏差；
3. 解决“**僵化**”问题：动态更新上下文，让 Agent 能根据任务进度、工具反馈，实时调整执行策略（比如旅行规划 Agent 调用天气 API 后，发现某天有雨，自动调整当天行程）。

大模型决定了 Agent 的“智商上限”，而上下文管理决定了 Agent 的“执行下限。


## 上下文的四大构成

### 短期记忆：
**定义**为本次会话（Session）内的所有交互记录、任务步骤、临时结论，比如你和 Agent 沟通时的每一句话、Agent 调用工具的结果、当前任务的进度。

**特点**：临时存储，任务结束后可清理，核心作用是“支撑单次任务的连贯执行。

在实际开发中，我们通常将同一个对话窗口内的所有交互视为一个 Session，开启新窗口就会初始化一个新的 Session ID，类似** ChatGPT 左侧的历史列表**，本质就是**不同 Session 的索引**。

### 长期记忆
**定义**为跨 Session 持久化存储的信息，比如用户的长期偏好、历史任务经验、领域固定知识（比如“用户喜欢极简风格的输出”“上次做旅行规划时，用户避开雨天景点”“Python 代码必须符合。

**特点**是长期存储、定期更新，核心作用是“实现跨任务的个性化和经验复用”，让 Agent 越来越“懂你”。

### 外部知识
**定义**为通过工具检索到的实时数据、专业文档、知识库信息。**特点**是按需检索、随任务更新，核心作用是“弥补大模型内置知识的时效性和领域局限性”——大模型的训练数据有滞后性，且无法覆盖所有细分领域，外部知识能解决这个问题。

### 环境状态
**定义**为工具调用的结果、外部系统的反馈、任务的实时进度，比如“调用 Excel 工具失败”“天气 API 返回未来5天有雨”“会议材料已发送至参会人邮箱”。

**特点**是实时更新，核心作用是“让 Agent 感知自己的动作效果”，从而动态调整执行策略——Agent 不是“单向输出”，而是“双向交互”，环境状态就是它的“反馈信号”。


## 怎么管理上下文

**核心目标**是在有限的上下文窗口（Token 限制）内，给 Agent 提供“恰到好处的信息”，不多也不少（多了会过载，少了会健忘）。

### 基础策略——滑动窗口

只保留最近 N 轮的交互记录（短期记忆），更早的记录直接丢弃，类似“手机聊天记录只显示最近100条”。
适用于**简单对话类 Agent**（比如智能客服、简单问答），任务流程短、不需要长期记忆。
**具体流程**是设定固定的“窗口大小”（比如最近5轮、8轮对话），当对话轮次超过窗口大小时，自动删除最早的对话记录——优点是实现简单、不消耗过多资源，缺点是会丢失早期关键信息，不适合复杂任务。

### 进阶策略——分层摘要
将上下文分为**当前工作层”和“历史摘要层**”，当前工作层保留最近 N 轮完整对话，历史摘要层将更早的对话用大模型压缩成摘要，既保留关键信息，又减少 Token 消耗——这是目前最常用的策略之一。
适用**多步骤复杂任务**（比如写文章、开发代码、项目规划），需要保留历史信息，但又不想占用过多 Token。
执行流程：

1. 设定“最大最近轮次”（比如8轮），超过这个轮次的对话，触发摘要压缩；
2. 用大模型将超出的对话压缩成1-2句摘要（比如“用户要求写一篇 AI Agent 上下文管理的文章，目标读者是新手，分浅中深三个层次”）；
3. 将摘要和当前最近轮次的对话，一起传给大模型，实现“既不健忘，又不过载”。

**优点**：Token 可控，能保留历史关键信息；**缺点**：摘要可能丢失部分细节，需要合理设定压缩时机（比如对话轮次超过 N 轮、Token 消耗超过 M 时触发）。


### 高阶策略——渐进式披露+动态注入
不要一次性把所有信息都交给 Agent，而是**分阶段、按需提供**（收缩+扩张结合），让 Agent 在每一步只看到“**当前需要的最小信息集**”，减少噪音、聚焦注意力——这是解决复杂 Agent“上下文爆炸”“工具过载”的核心方案。适用**复杂推理、多工具协作、企业级 Agent（**比如代码开发 Agent、项目管理 Agent）。

实操细节：

1.** L0层（常驻层）**：只保留任务目标、核心约束（比如“开发 Python 工具，符合 PEP8 规范”），长期驻留上下文，不轻易删除；

2.** L1层（索引层）**：提供信息索引（比如文件列表、数据库表名、工具大类），让 Agent 先“定位”信息，而不是直接提供全文；

3. **L2层（片段层）**：Agent 定位到相关信息后，再提供具体片段（比如代码片段、文档段落、工具详情），避免一次性加载过多内容。

例子：代码开发 Agent，初始只给 L0层（“开发批量处理 Excel 的 Python 工具”）和 L1层（“工具列表：Excel 操作工具、日志工具”）；Agent 选择 Excel 操作工具后，再给 L2层（Excel 工具的具体调用方法）——这样既能减少 Token 消耗，又能提高 Agent 的决策准确率。


### 终极策略——混合管理（生产级 Agent 落地方案）

核心逻辑：结合“锚定信息+分层摘要+RAG 检索”，兼顾稳定性、灵活性和实用性，是目前生产级 Agent 最常用的方案，能解决绝大多数复杂场景的需求。
核心组成（直接套用）：

1. **锚定信息**（永久驻留）：系统指令、任务目标、核心约束，永远不压缩、不删除，确保 Agent 不偏离方向；

2. **近期对话**（滑动窗口）：保留最近8-10轮完整对话，确保当前任务连贯；

3. **历史摘要**（分层压缩）：更早的对话压缩成摘要，减少 Token 消耗；

4. **RAG 检索**（按需调用）：接入向量数据库（比如 Milvus、Faiss），当 Agent 需要外部知识或历史长期记忆时，通过语义检索召回相关信息，动态注入上下文——向量数据库的优势是支持语意向量化，比传统数据库更容易实现语义相似检索，能快速找到和当前任务相关的信息。

答：上下文不是越多越好，是越准越好。噪声越多，幻觉越重。解决思路是：

1. 优化召回：少而精，不要多而杂：

- 控制召回数量：Top3～Top5 足够，别一股脑塞 Top10。
- 做 混合检索：向量 + BM25 互补，提高精准度。
- 加 阈值过滤：相似度低于阈值直接丢弃。

2. 重排序 Rerank;

-  用轻量交叉编码器 rerank 模型。
-   把最相关的排前面，不相关的直接丢掉。
-   模型注意力集中在真实信息上，幻觉大幅下降。

3. 上下文工程：清洗、去重、压缩。

- 语义去重，去掉重复段落。
- 长文本压缩 / 摘要，只保留关键信息。
- 结构化分段编号，让模型更容易识别来源。

4.  严格 Prompt 约束

- 只根据上下文回答。
-  禁止编造、禁止联想、禁止扩展。
- 引用原文片段作答。

5. 降低 chunk 大小，提高颗粒度

- chunk 越小越聚焦。
- 避免一大段里混杂无关信息。
- 召回更准，噪声更少。
