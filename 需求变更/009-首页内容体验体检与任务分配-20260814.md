## A. 写作师任务

### 1. [P0] 中间件文补深度——去掉"小白比喻"，补面试官会追问的底层

**问题场景**：首页 hero 写"对齐大厂面试官架构思维"、features 卡片写"中间件深度·底层逻辑"。但点开 `docs/java/redis/index.md`，通篇是"Redis 就像手机备忘录""和管理员沟通的人"，**一个底层机制都没讲**——RDB/AOF 的 fsync 策略、跳表、压缩列表、渐进式 rehash、缓存三大问题（穿透/击穿/雪崩）的真实解法全部缺席。冲着"大厂面试"来的核心受众，看到备忘录比喻会判定"这站太水"，直接流失。这是定位的根。

**方案**：

把中间件板块从"入门比喻文"重写为"深度面试文"。每篇至少讲透 3 个"面试官会追问"的深度点。以 Redis 为例，必须覆盖：

- **持久化**：RDB vs AOF 的取舍、AOF 的 `appendfsync`（always/everysec/no）三种策略对性能与可靠的影响、混合持久化
- **数据结构底层**：字符串 SDS、列表 quicklist、哈希 + 列表的压缩列表 ziplist、有序集合的跳表 skiplink、字典的渐进式 rehash
- **缓存问题**：穿透（布隆过滤器）、击穿（互斥锁/热点不过期）、雪崩（随机过期/熔断）的真实方案与代价
- 删除"小白能记住""就像手机备忘录"类措辞；命令演示保留，但要从"是什么"推进到"为什么这样设计"

**强制约束**：本任务受 `.claude/rules/content.md` 约束。写完必须过 content.md 的「生成后验收清单」（开头无空口承诺、结尾无升华、至少 1 个具体易错点、无 platitude、无对称结构、推荐有取舍）。通不过验收视为未完成。

**涉及文件**（写作师先盘点哪些已是深度文、哪些仍是比喻文）：
- `docs/java/redis/index.md`、`docs/java/redis/data-structures.md`、`docs/java/redis/persistence-cache-problems.md`
- 同步检查 `docs/java/mysql/`、`docs/java/kafka/`、`docs/java/spring/` 下各篇，凡比喻文一并改造

**验收**：每篇能讲出 ≥ 3 个面试官会追问的深度点；全篇无"备忘录/管理员"类比喻；通过 content.md 验收清单。

**工作量**：大（核心产出，建议和任务 11 合并推进——新写的直接写深度，省得返工）。

**优先级**：P0。

### 2. [P0] 首页删 platitude + 把差异化那句挪到显眼位置

**问题场景**：`docs/index.md:112-127` 的"为什么选择这个指南"五段——目标明确 / 体系完整 / 深度解析 / 实战导向 / 持续更新——逐条踩 content.md 黑名单（空口承诺 + platitude），每段都是放之四海皆准的形容词，信息量为零。老练读者一眼 AI 味。讽刺的是，`docs/index.md:46` 的 features 卡片里"系统设计算法：一致性哈希/限流/LFU——纯算法站不覆盖的差异化招牌"是**全站唯一一句有信息量的话**，却被埋在第 7 张卡。

**方案**：

- 删除 `docs/index.md:112-127` 整段五段 platitude，及结尾 `docs/index.md:131` 的读后感式收尾。
- 把"系统设计算法"这句差异化定位提炼到首页显眼位置（hero tagline 或紧贴 hero 的"本站差异点"小节），用"我们有什么 / 别人（牛客·小林 coding·JavaGuide）没有什么"的具体对比表达，不要用形容词。
- 首页 features 七张卡保留，但 `details` 文案去掉"深入理解""打好坚实基础"这类不可核对的话，换成具体覆盖点（如 MySQL 卡片改为"覆盖 B+ 树索引、MVCC、锁、explain 调优"）。

**强制约束**：受 content.md 约束，过验收清单。

**涉及文件**：`docs/index.md`。

**验收**：首页没有任何一句"删掉信息量不减"的形容词；差异点具体到能和竞品对照；features 卡片 details 每条都能从对应板块内容推导出来。

**工作量**：小（快赢，建议第一个做）。

**优先级**：P0。

### 3. [P1] 总览页只列真实存在的页面

**问题场景**：`docs/java/index.md:36-51` 的学习路线图列了 Spring Boot、微服务架构、分布式事务、JVM 调优、高并发系统设计实战——这些页面**都不存在**。用户按总览找内容 → 扑空 → 挫败。这是隐性死链，比显性死链更伤信任。

**方案**：

- 以 `docs/.vitepress/config.mts` 的 sidebar 为准（sidebar 已保证无死链），总览页只列真实存在的页面。
- 不存在的条目：要么删掉，要么标注"📝 待补"并给一个替代跳转（如"分布式事务 → 见 `/distributed/`"）。
- 一并核对其它板块总览：`docs/algorithm/index.md`、`docs/ai/index.md`、`docs/distributed/index.md`，凡承诺不存在的子页面同样处理。

**涉及文件**：`docs/java/index.md`、`docs/algorithm/index.md`、`docs/ai/index.md`、`docs/distributed/index.md`。

**验收**：每个总览条目都能点开真实页面，或在条目上明确标注"待补"。

**工作量**：小（主要是核对，不改内容深度）。

**优先级**：P1。
