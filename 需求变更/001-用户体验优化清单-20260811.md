## 背景

**目标用户画像**：正在准备 Java 后端社招面试的开发者，碎片化时间学习，移动端与桌面端混用，复习周期长且断续。

**核心目标**：把站点从"只能单向阅读的文档站"升级为"可追踪学习进度、可练习、移动端可用、能承接面试场景"的学习型产品，提升长期回访率。

**问题来源**：以用户视角通读首页（`docs/index.md`）、移动端样式（`docs/.vitepress/theme/custom.css`）、典型内容页（如 `docs/algorithm/00-algorithm-frameworks/sliding-window/index.md`）后，归纳出 14 处影响体验的问题。Top 4 为核心痛点，会直接导致用户流失；其余为体验瑕疵与功能缺口。

## 问题清单

### 1. [P0] 阅读进度持久化缺失（"继续学习"接不上）

**问题场景**：面试准备是长期、断续的。用户学到一半关掉浏览器，下次打开又是首页，完全想不起上次读到「滑动窗口」还是「Redis 持久化」。当前顶部进度条（已实现）只反映"本篇读到哪"，刷新即失，不解决"整个站点学到哪"。连续性是长期学习站的命脉。

**技术方案**：

定义统一的 localStorage 数据协议：

```
ik:reading-progress   → { [pageUrl]: { scrollRatio: 0~1, title, updatedAt } }   // 每篇阅读位置
ik:recent             → [ { url, title, visitedAt } ]                            // 最近访问（按时间倒序）
ik:bookmarks          → [ url ]                                                   // 收藏
ik:mastery            → { [pageUrl]: 'mastered' | 'learning' | 'todo' }          // 掌握状态
```

新增组件：

- `StudyTracker.vue`（注入 `layout-top`）：监听 `scroll`（rAF 节流）把当前 `route.path` 的滚动比例写入 `ik:reading-progress`；监听 `useRouter().onAfterRouteChanged` 把新地址 push 到 `ik:recent`。单点写入，所有其它组件只读。
- `ContinueReading.vue`：首页用，读 `ik:recent` / `ik:reading-progress` 取最近 3~5 篇，展示标题 + 进度条 + 「继续阅读 →」。
- `ArticleActions.vue`：文章页右下角浮层，三个按钮——收藏（写 `ik:bookmarks`）、标记掌握 / 学习中 / 待学（写 `ik:mastery`）。状态即时高亮。
- `MyProgressPanel.vue`（可选）：浮层面板或独立页 `/my-progress/`，汇总「收藏 / 已掌握 X 篇 / 最近阅读」。

**涉及文件**：新增 4 个 `.vue`；改 `docs/index.md`（插 `<ContinueReading />`）；改 `theme/index.ts`（注入 StudyTracker 与 ArticleActions）。

**工作量**：大（核心功能，需联调 4 个组件 + 数据协议 + 首页改造）。

**优先级**：P0。

### 2. [P0] 移动端侧边栏被强制隐藏

**问题场景**：`custom.css` 中存在：

```css
@media (max-width: 768px) {
  .VPSidebar { display: none; }
}
```

侧边栏在手机上直接消失，用户在地铁上打开「算法」板块，看不到该板块下有哪些文章，只能靠顶部下拉菜单一个个试，几乎不可用。

**技术方案**：删除上述 `display: none`。VitePress 默认主题在小屏本就提供「汉堡按钮 → 侧边栏抽屉滑出」的交互（`.VPNavBar.mobile .menu` 触发），当前被这条规则干掉了，恢复默认即可。需顺带验证：
- 粒子背景 `z-index:-1` 与抽屉层级不冲突
- `ReadingProgress` 进度条 `z-index:100` 不挡抽屉（抽屉默认更高，应无碍）
- 返回顶部按钮在抽屉打开时隐藏或降级

**涉及文件**：`docs/.vitepress/theme/custom.css`（删除/调整 `.VPSidebar` 隐藏规则，移动端段约第 105~144 行）。

**工作量**：极小（删几行 + 真机/DevTools 移动视口验证）。

**优先级**：P0。

### 3. [P0] 内容单向，代码不能跑、题目不能练

**问题场景**：作为"面试"知识库，用户只能读，与看 PDF 无差。代码块不能在页面内试运行；算法文末讲完框架没有任何承接——没有「去 LeetCode 刷 3 题」、没有自测题、没有难度标记。`custom.css` 中残留 `.question-card` / `.tag` / `#random-question-btn` 样式，是规划过但未实现的刷题功能"空壳"，对用户是"答应过却没兑现"。

**技术方案**（分三阶段，按投入产出比推进）：

- **阶段 A（低成本，建议先做）**：新增 `RelatedProblems.vue`，读文章 frontmatter 中的 `problems` 字段，渲染「相关题目」卡片列表：
  ```yaml
  ---
  problems:
    - title: 无重复字符的最长子串
      url: https://leetcode.cn/problems/longest-substring-without-repeating-characters/
      difficulty: medium
  ---
  ```
  点击直达 LeetCode，难度用颜色标签（easy 绿 / medium 橙 / hard 红）。逐篇补 frontmatter 即可上线。
- **阶段 B（中等）**：代码块增强——`config.mts` 开启 `markdown: { lineNumbers: true }`（行号，VitePress 内置）；超长代码（>30 行）默认折叠，用 Shiki transformer 给 `<pre>` 加 `class="collapsible"`，CSS `max-height` + 底部「展开」按钮。
- **阶段 C（高成本，后置）**：代码在线运行——接 Piston API（免费、多语言）做"运行示例代码"按钮；或嵌 LeetCode Playground。工程量大，建议在 A/B 见效后再评估。

**涉及文件**：新增 `RelatedProblems.vue`；改 `config.mts`（lineNumbers、shiki transformers）；改 `custom.css`（折叠样式）；逐篇 md 补 frontmatter。

**工作量**：阶段 A 小、B 中、C 大。

**优先级**：P0（A 阶段优先）。

### 4. [P0] 学习路径不可追踪

**问题场景**：首页「学习路径」是三行死文字（基础/进阶/高级阶段），不可点、不可追踪。用户读完不知道从哪开始、自己掌握多少、下一步该去哪。

**技术方案**：新增 `LearningPath.vue` 替换首页那段死文字：

- 分阶段（基础 / 进阶 / 高级）展示节点，每个节点对应 sidebar 中的关键页面（如「Java 基础」→ `/java/basics/`）
- 每个节点读 `ik:mastery`（与方案 1 共享协议）显示状态色：已掌握 / 学习中 / 待学
- 点击节点切换掌握状态，写回 `ik:mastery`
- 顶部展示总进度条「已掌握 X / Y 个核心知识点」
- 节点点击另一区域跳转到对应文章

**涉及文件**：新增 `LearningPath.vue`；改 `docs/index.md`（替换「学习路径」段）；依赖方案 1 的 `ik:mastery` 协议。

**工作量**：中（与方案 1 强联动，建议紧随其后做）。

**优先级**：P0。

### 5. [P1] 首页统计数字写死、不真实

**问题场景**：首页「数据看板」写死「150+ 知识点 / 200+ 题 / 30+ 项目 / 10+ 专栏」，与实际内容对不上，维护会失真，反让用户觉得不专业。

**技术方案**（二选一）：

- **方案 B（推荐，最快）**：去掉具体数字，改为定性描述（如「持续积累的知识库 · 覆盖后端 / 算法 / 分布式 / AI」），零维护。
- **方案 A（要真数据）**：写一个 VitePress 构建时插件（`config.mts` 的 `markdown` 或自定义 vite 插件），扫描 `docs/**/*.md` 数文件数、按板块统计，注入首页 frontmatter / 全局变量，组件运行时读取。真实但每次构建变。

**涉及文件**：`docs/index.md`；选 A 时新增构建脚本/插件。

**工作量**：B 极小、A 中。

**优先级**：P1。

### 6. [P1] Hero 图依赖外部 API，可能失效

**问题场景**：首页 hero `image.src` 指向 `https://trae-api-cn.mchost.guru/...`（外部 AI 文生图接口）。该服务一旦挂掉、限流或改接口，首页 hero 位就空一块或变图。

**技术方案**：把图片下载到本地 `docs/public/images/hero.png`，frontmatter 改为 `image.src: /images/hero.png`。本地资源稳定、可缓存、构建期打包。

**涉及文件**：新增 `docs/public/images/hero.png`；改 `docs/index.md` 的 hero image 字段。

**工作量**：极小。

**优先级**：P1。

### 7. [P2] 无反馈 / 纠错入口

**问题场景**：用户发现错别字或技术错误，没有渠道反馈，只能憋着，错误也就一直留着。

**技术方案**：新增 `FeedbackButton.vue`，文章页右下角浮一个「反馈纠错」按钮，点击跳转 GitHub Issue 预填模板：

```
https://github.com/handsomeyx/my-interview-king/issues/new
  ?title=[纠错] 当前页标题
  &body=页面路径：route.path%0A%0A问题描述：...
```

无后端、零成本。若想要轻量评论，可后续嵌 Giscus（基于 GitHub Discussions）。

**涉及文件**：新增 `FeedbackButton.vue`；改 `theme/index.ts`（注入）。

**工作量**：小。

**优先级**：P2。

### 8. [P1] 缺少定制 404 页

**问题场景**：点到死链时是 VitePress 默认英文 404，出戏，且没有引导动作。

**技术方案**：在 `theme/index.ts` 通过覆盖 `NotFound` 布局或使用 `Layout` 的 404 分支，渲染中文 404 页：配一句轻松文案 + 搜索框 + 「回首页 / 看热门」按钮。也可新增 `docs/404.md`（layout 自定义）。

**涉及文件**：改 `theme/index.ts`（NotFound 组件 / 插槽）；可选新增 404 layout 组件。

**工作量**：小。

**优先级**：P1。

### 9. [P2] 卡片 hover 动效过重，分散阅读注意力

**问题场景**：`custom.css` 中 `.VPFeature:hover` 设 `transform: translateY(-8px)` + 蓝色发光阴影。首页 6 个卡片每次鼠标扫过都大幅跳动 + 闪光，阅读时容易分心。

**技术方案**：

- 把 `-8px` 降到 `-2px` 或 `-3px`
- 发光阴影 `rgba(56,189,248,0.15)` 降到 `0.08` 左右
- 加 `@media (prefers-reduced-motion: reduce)` 关闭位移

**涉及文件**：`docs/.vitepress/theme/custom.css`（约第 254~283 行 `.VPFeature` 相关规则）。

**工作量**：极小（改几个数值）。

**优先级**：P2。

### 10. [P1] 深层页面无面包屑，不知身处哪一层

**问题场景**：在 `/algorithm/00-algorithm-frameworks/sliding-window/` 这类深层页，用户没有"当前位置"指示，容易迷失。

**技术方案**：新增 `Breadcrumbs.vue`，读 `useData()` 的 `page.relativePath` 或 `route.path`，按路径分段生成「首页 > 算法 > 算法框架 > 滑动窗口」。分段标题可：
- 从 `config.mts` 的 sidebar 配置反查（最准但需解析逻辑）
- 或按目录名硬编码一份映射表（简单）

通过 `doc-header-before` 插槽注入到文章顶部。

**涉及文件**：新增 `Breadcrumbs.vue`；改 `theme/index.ts`（注入）。

**工作量**：中（标题映射是主要工作量）。

**优先级**：P1。

### 11. [P2] 代码块仅"复制"，缺行号 / 折叠 / 语言标签

**问题场景**：长代码占满屏幕，无行号不便讨论「第 X 行」；60 行的 Java 把阅读节奏打断。

**技术方案**：

- 行号：`config.mts` 加 `markdown: { lineNumbers: true }`（VitePress 内置，一行配置）
- 折叠：见方案 3 阶段 B
- 语言标签：VitePress 默认已渲染语言名

**涉及文件**：`config.mts`（lineNumbers）；折叠部分与方案 3-B 共用。

**工作量**：行号极小、折叠中。

**优先级**：P2（与方案 3-B 合并实施）。

### 12. [P2] 无更新日志，用户不知最近更了什么

**问题场景**：回访用户不知道站点最近更新了哪些内容，缺乏"值得回来看"的信号。

**技术方案**（二选一）：

- **方案 A（推荐）**：新增 `docs/changelog.md`，手动维护「按日期倒序」的更新列表（新增 / 修订 / 修复），`config.mts` 的 nav 加「更新日志」入口。简单可控。
- **方案 B**：构建时从 `git log` 自动生成 changelog 页（按日期分组 commit message）。自动但 commit 质量参差时不好看。

**涉及文件**：新增 `docs/changelog.md`；改 `config.mts`（nav 入口）。

**工作量**：小。

**优先级**：P2。

### 13. [P2] 搜索无法按板块筛选

**问题场景**：用户只想在「Redis」板块内搜「持久化」，当前 local search 全站搜，结果噪声多。

**技术方案**（按复杂度，三选一）：

- **方案 C（务实推荐）**：每个板块顶部加一个「板块内搜索」小输入框，基于该板块 sidebar 的页面清单做简单标题/正文匹配（不接 minisearch），实现成本低。
- **方案 A（深度）**：扩展现有 `SearchPanel.vue`，加「范围：全部 / Java / 算法 / AI / 分布式」切换；在 VitePress local search 结果返回后按 `result.id` 前缀做后置过滤。需 hook 进搜索结果渲染，复杂度较高。
- **方案 B（换引擎）**：换 Algolia DocSearch（原生支持 facet 分面筛选），但要申请 + 配置 + 可能的构建期索引。

**涉及文件**：方案 C 新增组件；方案 A 改 `SearchPanel.vue`。

**工作量**：C 中、A 大、B 中（含接入）。

**优先级**：P2。

### 14. [P1] 图片放大 / 目录折叠在 SPA 路由后失效（bug）

**问题场景**：`theme/index.ts` 的 `setup().onMounted` 里给 `img` 绑定点击放大、给 `.outline-title` 绑定折叠，只在首次挂载执行一次。VitePress 是 SPA，路由切换到新文章后，新页面的图片和大纲标题不会再被绑定，导致"时灵时不灵"。

**技术方案**：

- 图片放大改为**事件委托**：在 `document` 级监听 `click`，用 `e.target.closest('img')` 命中则弹放大层。一次绑定、永久生效。
- 大纲折叠：VitePress 默认主题已自带大纲（右侧 TOC），可评估是否还需要自定义折叠；若保留，同样改事件委托或用 `useRouter().onAfterRouteChanged` 重新绑定。

**涉及文件**：`docs/.vitepress/theme/index.ts`（`onMounted` 内的图片放大与目录折叠段，约第 50~100 行）。

**工作量**：小。

**优先级**：P1（这是 bug 修复，非功能新增，应优先于 P2）。

## 实施建议顺序（分批推进）

**第一批 · 快赢修复（预计半天到一天）**
立竿见影、风险低。建议先做以快速建立正反馈：
- 14（SPA bug 修复）→ 2（移动端侧边栏）→ 6（Hero 图本地化）→ 9（hover 动效）→ 5-B（首页数据改文案）

**第二批 · 核心功能（预计 2~3 天）**
P0 主功能，相互联动：
- 1（阅读进度持久化，先定 localStorage 协议）→ 4（学习路径，复用 1 的协议）

**第三批 · 内容增强（预计 2~3 天）**
- 3-A（题目承接卡片）+ 11（代码行号/折叠）→ 10（面包屑）→ 8（404）→ 7（反馈入口）

**第四批 · 锦上添花（按需）**
- 12（更新日志）→ 13（搜索筛选）→ 3-B / 3-C（代码块进阶 / 在线运行）

每批完成后建议在本文档「状态」列更新进度，并在 `docs/changelog.md`（方案 12 落地后）记录。
