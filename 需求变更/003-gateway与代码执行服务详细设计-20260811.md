## 1. 阶段 1 范围与目标

### 1.1 做什么（最小可用）
- 起**基础设施**：Nacos（注册/配置）、Judge0（执行引擎）、Redis（限流）。**阶段 1 暂不起 PostgreSQL**（见决策点 D1）。
- **gateway**：路由 `/api/run` → code-exec-service，CORS，限流，预留鉴权过滤器（阶段 1 放行）。
- **code-exec-service**：单一端点 `POST /api/run`，同步调 Judge0，返回执行结果。
- **前端 CodeRunner** 改调 `http://localhost:8080/api/run` → 站点代码运行器**真正能用**。

### 1.2 不做什么（推到后续阶段）
- ❌ 题库 / 测试用例 / 判题（阶段 2+，需要 DB + 用户体系）
- ❌ 用户注册登录 / JWT 鉴权（阶段 2，user-service）
- ❌ 提交记录、学习进度（阶段 3）
- ❌ 异步判题 / 消息队列（阶段 3）
- ❌ 监控、链路追踪（阶段 5）

### 1.3 验收标准
1. `docker compose up` 一键起 Nacos + Judge0 + Redis + gateway + code-exec-service
2. 前端任意 Java/Python/JS 代码点「运行」→ 经 gateway → code-exec-service → Judge0 → 返回 stdout，**5 秒内出结果**
3. 超时/超内存/不支持语言等边界情况有正确反馈
4. 超过限流阈值返回 429

## 2. 整体与端口规划

```
浏览器 (VitePress, :5173)
   │  POST http://localhost:8080/api/run
   ▼
gateway (:8080)  ── 路由 + CORS + 限流(Redis) + [鉴权过滤器:阶段1放行]
   │  lb://code-exec-service
   ▼
code-exec-service (:8081, 仅内网)  ── 校验 + 组装 submission
   │  POST http://judge0server:2358/submissions?wait=true
   ▼
Judge0 (:2358, 仅内网) + judge0db(PostgreSQL) + judge0redis
```

| 组件 | 端口 | 暴露 | 说明 |
|---|---|---|---|
| VitePress 前端 | 5173 | 本机 | dev server |
| gateway | 8080 | 本机（上线公网） | 唯一入口 |
| code-exec-service | 8081 | 仅内网 | 不对外 |
| Nacos | 8848 | 仅内网 | 注册/配置 |
| Redis | 6379 | 仅内网 | 限流 |
| Judge0 server | 2358 | 仅内网 | 执行引擎 |
| Judge0 db/redis | - | 仅内网 | Judge0 专用 |

## 3. Gateway 详细设计

### 3.1 职责边界
**做**：路由转发、CORS、限流、请求日志、统一错误响应、（阶段2）JWT 验签与身份透传。
**不做**：业务逻辑、数据库访问、直接调 Judge0。

### 3.2 路由
```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: code-exec-run
          uri: lb://code-exec-service
          predicates:
            - Path=/api/run/**
          filters:
            - StripPrefix=0
        # 阶段2+ 追加：/api/problems、/api/auth、/api/progress 等
```
阶段 1 只一条路由 `/api/run/**`。后续阶段按服务边界追加，每服务一个路由块。

### 3.3 鉴权过滤器（阶段 1 简化）
- **阶段 1**：不验 token，全部放行。代码里**预留** `GlobalAuthFilter`（`Ordered` + `GatewayFilter`），读配置 `app.auth.enabled`，false 时直接 `chain.filter(exchange)`。
- **阶段 2**：`app.auth.enabled=true` + 配置白名单路径（`/api/auth/login` 等放行）+ JWT 验签 → 写入 `X-User-Id` / `X-User-Role` header 透传。
- 好处：阶段 2 只翻一个开关，不动路由。

### 3.4 限流（Redis 令牌桶）
- 维度：**客户端 IP**（阶段 1 无用户概念）。IP 获取：优先 `X-Forwarded-For`（上线 Nginx 透传），兜底 `remoteAddress`。
- 阈值（可配）：**每 IP 30 次/分钟**；**全局保护上限 600 次/分钟**（防恶意分布式）。
- 实现：Spring Cloud Gateway 内置 `RequestRateLimiter` + Redis RateLimiter（令牌桶）。
- 超限：返回 `429 TOO_MANY_REQUESTS`，响应头 `Retry-After: 2`。

### 3.5 CORS
```yaml
app:
  cors:
    allowed-origins:
      - http://localhost:5173       # 前端 dev
      - https://yourdomain.com      # 上线
    allowed-methods: [GET, POST, PUT, DELETE, OPTIONS]
    allowed-headers: [Content-Type, Authorization]
    allow-credentials: true
    max-age: 3600
```
允许前端跨域带凭证。配置化，从 Nacos 读。

### 3.6 统一错误响应
所有 4xx/5xx 走统一异常处理器，返回：
```json
{ "code": "RATE_LIMITED", "message": "请求过于频繁，请稍后再试", "data": null }
```
业务码（字符串，非 HTTP 数字）：`BAD_REQUEST` / `RATE_LIMITED` / `UNAUTHORIZED` / `SERVICE_UNAVAILABLE` / `INTERNAL_ERROR` 等。

### 3.7 请求日志
每个请求记：method、path、来源 IP、响应码、耗时。**不记请求体**（代码内容隐私 + 体积）。

## 4. Code-Exec-Service 详细设计

### 4.1 职责边界
**做**：接收 `/api/run` 请求 → 校验 → 组装 Judge0 submission → 同步调用 → 解析响应 → 返回标准化结果。
**不做**：鉴权（信任网关透传）、路由、限流（在网关）。

### 4.2 API：POST /api/run

**请求**：
```json
{
  "language": "java",          // 必填，枚举：java | python | javascript
  "code": "public class...",  // 必填，字符串
  "stdin": "可选输入"           // 可选，字符串
}
```

**成功响应**（200）：
```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "stdout": "3\n",
    "stderr": "",
    "exitCode": 0,
    "verdict": "OK",            // OK | TLE | MLE | RE | CE
    "timeMs": 120,
    "memoryKb": 24576
  }
}
```

**verdict 含义**：
| verdict | 触发 | 说明 |
|---|---|---|
| OK | exitCode=0 | 正常结束 |
| TLE | 触发 wall_time_limit | 超时 |
| MLE | 触发 memory_limit | 超内存 |
| RE | exitCode≠0 且非上面 | 运行时错误（含被 kill） |
| CE | Judge0 编译失败 | Java/编译型语言编译错 |

**错误响应**（4xx/5xx，统一格式）：
| HTTP | code | 触发 |
|---|---|---|
| 400 | `BAD_REQUEST` | language 缺失/不支持、code 为空 |
| 413 | `PAYLOAD_TOO_LARGE` | code 超 64 KB 或 stdin 超 1 MB |
| 422 | `COMPILE_ERROR` | 编译失败（也可放 200 + verdict=CE，见决策点 D8） |
| 503 | `SERVICE_UNAVAILABLE` | Judge0 不可达 / 自身异常 |
| 504 | `GATEWAY_TIMEOUT` | 调 Judge0 超过自身等待上限（如 15s） |

### 4.3 Judge0 集成

**语言映射**（配置化，不写死代码）：
```yaml
app:
  judge0:
    base-url: http://judge0server:2358
    wait-timeout-seconds: 15      # 调 Judge0 的整体超时
    languages:
      java:        { id: 62,  version: "17.0.6",  file: "Main.java" }
      python:      { id: 71,  version: "3.10",    file: "main.py" }
      javascript:  { id: 93,  version: "18.15.0", file: "main.js" }
```
> **注**：`id` 是 Judge0 的 languageId，**需在部署后用 `GET /languages` 核对**（不同 Judge0 发行版 ID 可能不同）。设计上 id 放配置，不改代码即可调。

**调用模式**：同步 `POST /submissions?base64_encoded=false&wait=true`，Judge0 在 `wall_time_limit` 内阻塞返回结果。

**submission 字段**：
```json
{
  "language_id": 62,
  "source_code": "...",
  "stdin": "...",
  "cpu_time_limit": 2,
  "wall_time_limit": 5,
  "memory_limit": 262144,
  "max_processes_and_or_threads": 10
}
```

**重试策略**：Judge0 偶发 5xx 或网络抖动 → 重试 1 次（间隔 500ms）。超时/4xx 不重试。

### 4.4 资源限制（默认值，可配）
| 项 | 默认 | 说明 |
|---|---|---|
| cpu_time_limit | 2 秒 | CPU 时间 |
| wall_time_limit | 5 秒 | 真实时间（含阻塞），判 TLE |
| memory_limit | 262144 KB（256 MB） | 判 MLE |
| max_processes | 10 | 防 fork 炸弹 |
| code 最大长度 | 64 KB | 网关/服务双层校验 |
| stdin 最大长度 | 1 MB | 防超大输入 |

### 4.5 错误处理与降级
- **Judge0 连接失败** → 503 + 日志（不打断服务，返回友好提示）
- **Judge0 响应超 15s** → 504（client 端先于 Judge0 wall_time 兜底）
- **Judge0 返回非预期结构** → 502 + 完整响应体写日志（便于排查）
- **服务自身异常**（空指针等） → 500 + 全局异常处理器兜底

### 4.6 日志
每次 `/api/run` 记：language、code 长度、verdict、timeMs、memoryKb、来源 IP（网关透传）、traceId。**不记 code 全文**（隐私 + 体积），可选记 code 的 SHA-256 用于关联排查。

## 5. 不确定点与边界条件（请你逐项定）

| # | 决策点 | 选项 | 我的推荐 |
|---|---|---|---|
| D1 | 阶段 1 是否起 PostgreSQL | A 不起（/api/run 无状态） / B 起（预留，不连） | **A 不起**（阶段 2 接 DB 时再起，少一个依赖） |
| D2 | 鉴权策略 | A 完全放行 / B 简单 API Key / C 临时写死用户 | **A 放行**（阶段 2 user-service 上线后接 JWT） |
| D3 | 限流维度与阈值 | A 30 次/分/IP / B 60 / C 按 token（阶段 2） | **A 30 次/分/IP + 全局 600/分**，可调 |
| D4 | 首批支持语言 | A 仅 Java / B Java+Python / C Java+Python+JS / D 更多 | **C 三样**（覆盖你算法+后端+AI 板块） |
| D5 | 资源限制默认 | A 2s/256MB / B 5s/512MB / C 自定义 | **A 2s/256MB**（判题够用，防滥用） |
| D6 | 代码长度上限 | A 16KB / B 64KB / C 256KB | **B 64KB**（足够长算法题） |
| D7 | 错误响应格式 | A 统一封装 `{code,message,data}` / B 原样 HTTP 状态 | **A 统一封装**（前端处理一致） |
| D8 | 编译错误（CE）如何返回 | A 200 + verdict=CE + stderr / B 422 单独错误 | **A 200+verdict=CE**（前端统一走输出区，不弹错误） |
| D9 | 仓库位置 | A 现有项目 `backend/` 子目录（monorepo）/ B 独立新仓库 | **A backend/ 子目录**（与前端同仓，便于联调，后续可拆） |
| D10 | Judge0 发行版 | A Judge0 CE（基础 50+ 语言）/ B Extra CE（60+ 含新版本） | **B Extra CE**（Java 17、Python 3.10+ 更全） |
| D11 | 是否记录代码全文到日志 | A 不记（只元数据）/ B 记（便于复现） | **A 不记**（隐私+体积；记 SHA-256 可关联） |
| D12 | 前端 baseURL 环境变量名 | A `VITE_BACKEND` / B `VITE_API_BASE` | **A `VITE_BACKEND`** |
| D13 | Judge0 调用是否做结果缓存 | A 不缓存（每次实跑）/ B 同代码同输入缓存 | **A 不缓存**（阶段 1 简单；缓存判题场景放阶段 2） |
| D14 | 服务端口 | gateway 8080 / code-exec 8081 | 固定，如冲突可调 |

### 边界条件（我的处理方式，如有异议告诉我）

| 场景 | 处理 |
|---|---|
| `code` 为空字符串 | 400 `BAD_REQUEST`「代码不能为空」 |
| `language` 不在支持列表 | 400 `BAD_REQUEST`「不支持的语言: xxx」 |
| `code` 超 64 KB | 413 `PAYLOAD_TOO_LARGE` |
| `stdin` 超 1 MB | 413 `PAYLOAD_TOO_LARGE` |
| 同一请求体巨大（JSON 炸弹） | 网关层限制 Content-Length ≤ 100 KB |
| Judge0 容器未启动 / 重启中 | 503 `SERVICE_UNAVAILABLE`「执行服务暂不可用」 |
| Java 编译失败（类名/语法错） | 200 + verdict=CE + stderr 含编译错误 |
| 死循环代码 | wall_time_limit=5s 触发 → verdict=TLE |
| 内存泄漏/分配巨大 | memory_limit 触发 → verdict=MLE |
| 代码读文件/起网络连接 | Judge0 容器隔离，操作失败 → verdict=RE |
| 并发突发（同一 IP 高频） | 网关限流 429 |
| Judge0 返回乱码/非 UTF-8 | 强制以 UTF-8 解析，替换非法字符 |

## 6. 部署（阶段 1 docker-compose 节选）

```yaml
services:
  # ── 基础设施 ──
  nacos:
    image: nacos/nacos-server:v2.3.0
    ports: ["8848:8848"]
    environment:
      - MODE=standalone
  redis:
    image: redis:7-alpine
    ports: ["6379:6379"]

  # ── Judge0（仅内网，不映射宿主端口到公网）──
  judge0server:
    image: judge0/judge0:1.13.0
    expose: ["2358"]            # 仅容器网络可见
    environment:
      - REDIS_URL=redis://judge0redis:6379
      - POSTGRES_HOST=judge0db
      - POSTGRES_USER=judge0
      - POSTGRES_PASSWORD=judge0
      - JUDGE0_MAINTENANCE_INTERVAL=5
    depends_on: [judge0redis, judge0db]
  judge0redis: { image: redis:7-alpine }
  judge0db: { image: postgres:15, environment: { POSTGRES_DB: judge0, POSTGRES_USER: judge0, POSTGRES_PASSWORD: judge0 } }

  # ── 业务服务 ──
  gateway:
    build: ./backend/gateway
    ports: ["8080:8080"]
    depends_on: [nacos, redis]
  code-exec-service:
    build: ./backend/code-exec-service
    expose: ["8081"]
    depends_on: [nacos, judge0server]
```

启动顺序：基础设施 → Judge0 → 业务服务。docker-compose 的 `depends_on` 只保证启动顺序不保证就绪，首次启动需等 Nacos/Judge0 初始化（~30 秒）。
