## 1. 概述

### 1.1 背景
Piston 公共 API 2026/2/15 起白名单停服，代码运行功能失去执行环境。Java 无法在浏览器执行（JVM 过大），必须自主服务端执行环境。借此契机自建**微服务后端**：首发「代码执行服务」解决运行/判题，后续按业务边界拆出「用户服务」「内容服务」「进度服务」等，承载鉴权、内容管理、学习进度云同步。

### 1.2 目标
- 自主代码执行环境（Java/Python/JS/C++ 等），无外部 API 依赖
- LeetCode 式判题（测试用例 + 期望输出 + 通过/失败 + 资源限制）
- 微服务架构：服务按业务边界拆分，独立开发/部署/扩缩
- 可扩展：新服务（用户/内容/进度/通知）按既定协议接入

### 2.1 服务拆分清单

| 服务 | 职责 | 库 | 状态 |
|---|---|---|---|
| **gateway** | 统一入口、路由、JWT 验签、限流、透传用户身份 | 无（无状态） | 阶段1 骨架 |
| **code-exec-service** | 代码执行（/api/run）、题库、判题、提交记录 | code_exec_db | **阶段1 首发** |
| **user-service** | 注册/登录、JWT 签发、用户资料、角色 | user_db | 阶段2 |
| **progress-service** | 学习进度、收藏、刷题统计（替代前端 localStorage） | progress_db | 阶段3 |
| **content-service** | 文章/题目元数据 CRUD、动态内容 | content_db | 阶段4 |
| **notification-service**（可选） | 站内信、邮件、Webhook | notify_db | 远期 |

**拆分原则**：按**业务能力**（不是按技术层），每个服务**独立数据库**（database-per-service），跨服务走 API/事件、不跨库 join。

## 3. 技术方案

### 3.1 服务注册发现与配置中心（Nacos）

- 所有服务启动注册到 Nacos，网关从 Nacos 发现服务实例做负载均衡路由
- 配置集中管理：`application.yml` 按 `dataId = ${service}-${env}.yaml` 存 Nacos，改配置不重新部署
- 多环境：`dev` / `prod` namespace 隔离

### 3.2 API 网关（Spring Cloud Gateway）

**核心职责**：
1. **路由**：`/api/run/**` → code-exec-service；`/api/auth/**` → user-service；等等
2. **鉴权前置**：全局过滤器验 JWT → 解析 userId → 写入 `X-User-Id` header 透传下游
3. **限流**：基于 Redis（令牌桶），按 userId/IP 维度，保护判题服务
4. **CORS**：统一处理跨域（前端 VitePress 与后端不同源）

**路由表示例**：
```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: code-exec
          uri: lb://code-exec-service
          predicates: [ Path=/api/run/**, Path=/api/problems/**, Path=/api/submissions/** ]
        - id: user
          uri: lb://user-service
          predicates: [ Path=/api/auth/**, Path=/api/me/** ]
        - id: progress
          uri: lb://progress-service
          predicates: [ Path=/api/progress/**, Path=/api/bookmarks/** ]
```

### 3.3 服务间通信

| 模式 | 场景 | 技术 |
|---|---|---|
| 同步 | code-exec 查用户信息（提交归属）、网关→服务 | OpenFeign（声明式 HTTP） |
| 异步 | 判题完成通知、进度更新事件 | RabbitMQ（事件总线） |
| 事件 | 用户注册成功 → progress 初始化默认进度 | RabbitMQ fanout |

**契约**：Feign 接口定义在 `common` 模块，服务间共享 DTO。事件用统一 `Event<T>` 包装（eventType、timestamp、payload）。

### 3.4 鉴权方案（微服务下）

```
前端登录 → user-service 验密码 → 签 JWT（含 userId、role）
前端带 JWT → Gateway 验签 + 解析 → 透传 X-User-Id / X-User-Role header
下游服务从 header 取身份（信任网关，不再验签）→ 业务逻辑
```

- **Access Token**：15 分钟，Redis 存 blacklist 支持登出
- **Refresh Token**：7 天，Redis 存，可吊销
- **服务信任链**：服务不直接对外，只信网关透传的 header（服务端口不暴露公网）
- **服务间 Feign**：通过拦截器透传 `X-User-Id`

### 3.5 数据架构（每服务独立库）

```
PostgreSQL 实例（开发期单实例多库，上线可拆多实例）
├── code_exec_db   problems, test_cases, submissions, languages
├── user_db        users, roles
├── progress_db    progress, bookmarks, stats
└── content_db     articles, problem_metadata
```

**铁律**：服务不访问他服务的库；跨服务数据走 API。需要聚合（如题目页显示作者信息）由前端组合调用或网关 BFF 聚合。

## 4. 代码执行服务（code-exec-service）★ 当前实施重点

### 4.1 职责
- `/api/run`：执行单段代码（无判题），CodeRunner 直接调
- `/api/problems` `/api/problems/{id}`：题库 CRUD + 代码模板
- `/api/problems/{id}/submit`：判题（多测试用例批量执行 + 比对 + 通过/失败）
- `/api/submissions`：提交历史

### 4.2 数据模型
```java
Problem {
  id, slug, title, description,   // 题目元数据
  difficulty(EASY/MEDIUM/HARD),
  tags[],
  timeLimitMs(默认2000), memoryLimitKb(默认262144),
  templates{java, python, javascript},   // 各语言代码模板
  status(DRAFT/PUBLISHED)
}

TestCase {
  id, problemId,
  input,           // stdin
  expectedOutput,  // 期望 stdout
  isSample,        // 是否示例（公开）
  ordinal          // 顺序
}

Submission {
  id, userId, problemId,
  language, code,
  verdict(AC/WA/TLE/MLE/RE/CE),
  passedCount, totalCount,
  timeMs, memoryKb,
  judge0Token,     // Judge0 submission token（追溯）
  createdAt
}

Language { id(Judge0 languageId), name, version, enabled }
```

### 4.3 Judge0 集成

**部署**（docker-compose 节选）：
```yaml
judge0server:
  image: judge0/judge0:1.13.0
  ports: ["2358:2358"]      # 仅内网，不暴露公网
  environment:
    - REDIS_URL=redis://judge0redis:6379
    - POSTGRES_HOST=judge0db
    - JUDGE0_MAINTENANCE_INTERVAL=...
  depends_on: [judge0redis, judge0db]
judge0redis: { image: redis:7 }
judge0db:    { image: postgres:15 }
```

**调用模式**：
- **同步**（`/api/run`）：POST `/submissions?base64_encoded=false&wait=true`，等结果直接返回。适合短代码即时运行。
- **异步**（`/api/problems/{id}/submit` 判题）：POST 多个 submission 拿 token → 轮询或回调拿结果。适合多用例判题，配合 RabbitMQ 解耦。

**安全与资源限制**（每次 submission）：
```java
{ cpu_time_limit: 2, wall_time_limit: 5, memory_limit: 262144, max_processes: 10 }
```
- 超时/超内存 → TLE / MLE
- 代码长度上限 64 KB
- Judge0 在 Docker 容器内隔离执行，无宿主访问
- 网关层额外限流：每用户 30 次/分钟

### 4.4 容错
- Judge0 不可用：返回 `503 SERVICE_UNAVAILABLE` + 友好提示，前端 CodeRunner 显示"执行服务暂不可用"
- 判题超时：单 case 超时标记 TLE，继续跑其他 case
- 限流触发：返回 `429`，前端提示"操作过于频繁"

## 6. 部署架构

### 6.1 开发期（本机 docker-compose）

根目录 `docker-compose.yml` 一键起基础设施 + 全服务：
```yaml
services:
  # 基础设施
  nacos:      { image: nacos/nacos-server:v2.3.0, ports: ["8848:8848"] }
  postgres:   { image: postgres:15, ports: ["5432:5432"] }
  redis:      { image: redis:7, ports: ["6379:6379"] }
  rabbitmq:   { image: rabbitmq:3.12-management, ports: ["5672:5672","15672:15672"] }
  judge0server + judge0db + judge0redis: (见 4.3)

  # 业务服务（每个 Spring Boot 打成镜像）
  gateway:            { build: ./gateway,            ports: ["8080:8080"], depends_on: [nacos] }
  code-exec-service:  { build: ./code-exec-service,  depends_on: [nacos, postgres, redis, judge0server] }
  # user/progress/content 服务阶段接入时追加
```

启动：`docker compose up -d`，前端 `VITE_BACKEND=http://localhost:8080`。

### 6.2 上线
- 云服务器（2C4G 起步够判题；流量大可独立升配 Judge0 节点）
- Nginx 反代：`yourdomain.com/api/*` → gateway:8080；`yourdomain.com/*` → 前端静态产物
- HTTPS：Let's Encrypt
- Judge0 / PostgreSQL / Redis / RabbitMQ 仅内网，不暴露公网
- 监控：Spring Boot Actuator + Prometheus + Grafana（可选）

## 7. 渐进式实施路线（关键：避免 over-engineering）

> **强烈建议**：微服务虽是最终形态，但**不要一上来全拆**。按下方阶段渐进，每阶段独立可验收、可上线。

### 阶段 1 · 基础设施 + 代码执行服务 + 网关骨架（1-2 天）★ 当前
- 起 Nacos / PostgreSQL / Redis / Judge0（docker-compose）
- 建 Maven multi-module 仓库（gateway / code-exec-service / common）
- **gateway**：路由 + CORS + 简单鉴权过滤器（暂不强制，先放行）
- **code-exec-service**：`/api/run` 代理 Judge0（同步），含 Judge0 集成 + 资源限制 + 限流
- 前端 CodeRunner 改调 `http://localhost:8080/api/run`
- **验收**：前端任意 Java/Python/JS 代码能跑出输出 → 代码运行器**真正可用**

### 阶段 2 · 用户服务 + JWT 鉴权接入（2 天）
- 拆出 user-service（注册/登录/签 JWT）
- 网关接入 JWT 验签 + 透传 X-User-Id
- code-exec-service 的 `/api/submissions` 接入鉴权，记录提交归属
- **验收**：用户登录后提交判题，记录归该用户

### 阶段 3 · 进度服务 + 异步判题（2-3 天）
- 拆出 progress-service（进度/收藏/统计）
- 引入 RabbitMQ：判题完成事件 → progress 更新统计
- 判题改异步（多 case 批量）
- 前端 localStorage 数据迁移到云端（首次登录同步）
- **验收**：学习进度、收藏、刷题统计多端同步

### 阶段 4 · 内容服务 + 题库完善（持续）
- 拆出 content-service，文章/题目动态化
- 题库批量录入（关联 LeetCode 题号、难度、标签）
- 前端 RelatedProblems 接入真实题库

### 阶段 5 · 加固（按需）
- 监控（Prometheus + Grafana）、链路追踪（SkyWalking/Zipkin）、日志聚合（ELK）
- 限流/熔断（Sentinel）、灰度发布

## 9. 工程量与风险

### 9.1 总工程量
| 阶段 | 工程量 | 累计 |
|---|---|---|
| 1 基础设施 + 代码执行 + 网关骨架 | 1-2 天 | 2 天 |
| 2 用户服务 + 鉴权 | 2 天 | 4 天 |
| 3 进度服务 + 异步判题 | 2-3 天 | 7 天 |
| 4 内容服务 + 题库 | 持续 | - |
| 5 监控加固 | 按需 | - |

（基于熟悉 Spring Boot 的估算；如生疏，每阶段 ×1.5）

### 9.2 风险与缓解
| 风险 | 缓解 |
|---|---|
| 微服务 over-engineering（个人项目） | **严格走渐进式**，阶段 1 只起 1 业务服务 + 基础设施，跑通再拆 |
| Judge0 多容器部署复杂 | docker-compose 一键起，照官方模板 |
| 代码执行安全 | Judge0 容器隔离 + 网关限流 + 资源限制 |
| 服务间数据一致性 | 遵循 database-per-service，跨服务走 API/事件 + 最终一致 |
| 调试复杂（多服务） | 本机 docker-compose 统一日志；SkyWalking 链路追踪（阶段5） |
| 学习曲线（Spring Cloud 全家桶） | 你是 Java 后端方向，这是面试核心技能，边做边精练 |

## 10. 前端对接（CodeRunner 改造）

当前 CodeRunner 调 Piston，阶段 1 完成后改 20 行对接后端：

```js
// CodeRunner.vue
const BACKEND = import.meta.env.VITE_BACKEND || 'http://localhost:8080'

const runCode = async (code, lang, stdin, outEl, stEl) => {
  const res = await fetch(`${BACKEND}/api/run`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ language: lang, code, stdin })
  })
  const data = await res.json()   // { stdout, stderr, exitCode, timeMs, memoryKb }
  // ... 渲染输出
}
```

`.env`（前端）：
```
VITE_BACKEND=http://localhost:8080
```
