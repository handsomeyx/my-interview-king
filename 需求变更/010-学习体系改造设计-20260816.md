# 学习体系改造设计

> 写给内容创作者：本文档定义了「我是面试大王」学习体验的整体改造方向和具体写法规范。目标是让读者在阅读每一篇文章时，不仅能"看懂"，更能"想清楚、讲出来、记得住"。

---

## 一、设计理念

### 现状的短板

目前站点的内容组织已经很扎实：覆盖面广、有追问深度、有易错点提醒。但整体上仍是"读者在看，知识在书里"的被动模式——读者看完一篇文章，觉得自己懂了，但过两天被问起，可能说不清。

原因很简单：**阅读是最浅层次的学习。** 真正的理解需要主动输出。

### 改造目标

给每篇文章装上"思考钩子"，让读者在被动阅读的同时，不断被引导去主动思考、用自己的话复述、在脑海里建立跨主题的连接。

具体要实现四个转变：

| 转变 | 说明 |
|------|------|
| 从"读知识点"到"建立认知锚点" | 每篇文章开头给一个"为什么存在"的思考点，不直接给结论，引导读者自己推导出技术方案 |
| 从"记住结论"到"能用自己的话讲给别人听" | 每篇文章结尾有引导性的复述环节，强迫读者检测自己是否真的理解了 |
| 从"单点学习"到"建立跨域连接" | 把分散在不同板块的知识点串联起来，让读者能看到"不同技术在解决同一类问题" |
| 从"一次学会"到"间隔复习" | 读者标记掌握后，系统在合适的时机提醒回来重新复述，对抗遗忘 |

---

## 二、具体改造方向

### 改造 A：每篇文章开头增加「思考锚点」段落

#### 位置

放在文章标题和 `---` 分隔线之后、正文 Q&A 之前。

#### 写法规范

这个段落的目的是：在读者接触到具体的技术细节之前，先用 3-5 句话引导他们思考"这个技术到底在解决什么不可回避的问题"。

**写法步骤：**

1. 先讲这个问题的**物理/工程事实**（不可改变的约束条件）
2. 再讲如果不解决这个问题会导致什么**具体后果**
3. 最后用一句话点出"本文介绍的技术就是为了解决这个问题而存在的"

**不需要写结论**——让读者带着"哦？那它是怎么做到的"的好奇往下读。

#### 示例

以 `volatile-jmm.md` 为例：

> ```markdown
> ## 思考锚点
>
> 现代 CPU 都是多核的，每个核心有自己的缓存。当一个核心修改了变量值，其他核心不会自动看到——因为每个核心的缓存里存的还是旧值。
>
> 同时，编译器和 CPU 为了性能会调整指令执行顺序，只要单线程结果不变就行。但在多线程环境下，这种重排可能导致一个线程还没初始化完对象，另一个线程就开始使用它了。
>
> volatile 就是 JVM 层面给程序员的一个"开关"，告诉编译器和 CPU："这个变量不要缓存、不要重排"。
> ```

以 `basics.md`（分布式基础）为例：

> ```markdown
> ## 思考锚点
>
> 单机系统里，一个变量要么存在内存里要么不存在，所有操作都经过同一个 CPU，所以"数据一致"是默认保证的。
>
> 但一旦数据分布在多台机器上，每台机器各算各的，"一致"就变成了一个需要专门设计才能保证的东西。CAP 理论就是在说：面对网络分区这种不可回避的情况，你必须在"所有节点数据同步"和"每个节点都能响应请求"之间做取舍，不可能两头都占。
>
> 本文讲的就是分布式系统里最核心的几个取舍框架和工程解法。
> ```

#### 适用范围

所有标注了"核心深度"的文章。具体包括：

- Java 板块：volatile/jmm、synchronized/lock、线程池、ThreadLocal、JVM GC、类加载、Spring IoC/AOP、事务、循环依赖、MySQL 索引/MVCC/锁、Redis 持久化/缓存问题、Kafka 副本
- 分布式板块：CAP/BASE、一致性哈希、Raft、分布式锁、分布式事务
- 算法板块：各框架文（滑动窗口、动态规划、二分、DFS/BFS 等）
- AI 板块：Agent 核心概念、MCP 协议、RAG 基础

### 改造 B：每篇文章结尾增加「复述自测」引导

#### 位置

放在文章最后一个章节之后，`---` 分隔线之前。

#### 写法规范

这个环节的目的是：在读者读完之后，引导他们用自己的话把刚学的东西讲一遍。不是考记忆力，而是帮读者检测自己是否真的"想通了"。

**三个引导问题，每个 1-2 句话引导即可：**

| 问题 | 作用 |
|------|------|
| **"用一句话说，这个技术/算法是用来解决什么问题的？"** | 检验读者能否提炼核心（很多人看完能背细节但说不清用途） |
| **"假设你对面坐着一个只懂基础语法的初学者，你怎么用生活里的例子给他讲清楚？"** | 检验读者是否真的理解（不能用专业术语，必须转化成朴素语言） |
| **"你觉得哪些地方是面试时最容易被追问住的？"** | 帮读者主动预判薄弱环节，同时为面试做准备 |

#### 示例

以 `volatile-jmm.md` 为例：

> ```markdown
> ## 复述自测
>
> 读完这篇，试试用自己的话回答三个问题：
>
> 1. **一句话总结**：volatile 到底是做什么的？（提示：别只说"可见性和有序性"，想想它解决的物理事实是什么）
>
> 2. **讲给初学者听**：如果让你给一个大一新生解释"为什么需要 volatile"，你会怎么说？可以用"多人协作时信息不同步"、"传话游戏传错顺序"之类的类比。
>
> 3. **预判追问**：如果你是面试官，看完这篇你会追问候选人什么？（比如 volatile 和 synchronized 有什么区别？为什么 volatile 的 i++ 不安全？）
> ```

以 `basics.md`（分布式基础）为例：

> ```markdown
> ## 复述自测
>
> 读完这篇，试试用自己的话回答三个问题：
>
> 1. **一句话总结**：CAP 到底在说什么？为什么"三选二"的说法容易被骂？
>
> 2. **讲给初学者听**：用"一群人分坐不同房间传话"之类的类比，讲讲什么是网络分区、为什么 CAP 里的 P 是必须接受的。
>
> 3. **预判追问**：如果你是面试官，读完这篇你会追问什么？（比如为什么注册中心倾向 AP？Raft 里的多数派是怎么保证一致性的？）
> ```

#### 重要说明

这个环节**不需要提供答案**。它的价值恰恰在于"读者自己去找答案"这个过程。如果读者答不上来，自然会回头重看相关段落——这本身就是最好的学习。

#### 适用范围

与"思考锚点"相同的文章范围。

### 改造 C：建立「跨域关联」提示

#### 位置

在文章侧边栏底部（现有 RelatedProblems.vue 的位置下方，新增一个"相关思考"区域）或在文章末尾"复述自测"之后。

#### 写法规范

这个环节的目的是：帮助读者发现"不同技术领域的知识点之间存在的同构关系"——也就是说，表面上不相关的技术，底层其实在解决同一类问题。

**每条关联用一句话表达：**

```
💡 你知道吗？[技术 A] 和 [技术 B] 其实在解决同一类问题：[底层共性]
```

#### 示例

以 `volatile-jmm.md` 为例，可以加：

> ```markdown
> 💡 相关思考
>
> 你知道吗？volatile 的"内存屏障"和分布式系统里的"顺序一致性"其实在解决同一类问题——在并发环境下保证操作的执行顺序可预测。CPU 层面靠硬件指令，分布式层面靠协议（如 Raft 的日志复制顺序），本质上是在做同一件事。
> ```

以 MySQL 索引篇为例，可以加：

> ```markdown
> 💡 相关思考
>
> 你知道吗？MySQL 的 B+ 树索引、Redis 的跳表、HashMap 的链表 + 数组，它们的底层目标是一致的：在"查找效率"和"更新效率"之间找一个工程上可接受的平衡点。不同场景下选择不同数据结构，本质上是在不同的读写比例下做权衡。
> ```

以一致性哈希篇为例，可以加：

> ```markdown
> 💡 相关思考
>
> 你知道吗？一致性哈希里的"虚拟节点"思路，和负载均衡里的"加权轮询"、以及数据库分片里的"取模分片"改进方案，其实都是在解决同一个问题：如何在资源节点不均匀的情况下，让请求/数据分布得更均匀。
> ```

#### 维护方式

不需要每篇都写。**在每完成一个核心知识域后，集中维护一个跨域关联表**，然后把关联分发到相关文章里。建议维护一个 `docs/.vitepress/thinking-links.json` 文件，格式如下：

```json
{
  "links": [
    {
      "from": "/java/concurrent/volatile-jmm",
      "to": ["/distributed/basics", "/java/concurrent/lock"],
      "text": "volatile 的内存屏障和分布式系统的顺序一致性在解决同一类问题：并发环境下的操作顺序保证。"
    },
    {
      "from": "/java/mysql/indexing",
      "to": ["/java/redis/data-structures", "/algorithm/02-data-structures/tree/"],
      "text": "B+ 树、跳表、哈希表都在做同一件事：在查找和更新之间找工程平衡点。"
    }
  ]
}
```

然后在 `RelatedProblems.vue` 旁边新增一个 `ThinkingLinks.vue` 组件，读取这个 JSON 自动渲染。

### 改造 D：文章中穿插「读者思考」微提示

#### 位置

在长段落或复杂推导的中间，用一个小的引用块打断阅读节奏。

#### 写法规范

当文章里出现了关键推导步骤（比如"从物理事实推导出设计约束"的环节），在中间插入一个引导思考的小提示，让读者暂停几秒，自己想一想。

**格式：**

```
> 🤔 停下来想想：[具体的引导性问题]
```

**关键：这个问题不需要很深奥，但必须让读者"停下来想"。**

#### 示例

在讲 Raft 日志复制时，中间可以加：

> ```markdown
> Leader 写本地日志后，需要同步给所有 Follower。这里有一个关键设计决策：是等所有 Follower 都确认后再提交，还是只要多数 Follower 确认就提交？
>
> 🤔 停下来想想：如果等所有 Follower 都确认，会有什么问题？如果只要多数确认，又是什么保证了"已经提交的日志不会被新 Leader 推翻"？
> ```

在讲 MySQL MVCC 时，中间可以加：

> ```markdown
> 每一行数据都有两个版本号：创建版本和删除版本。查询时根据事务自己的版本号来决定哪些行可见。
>
> 🤔 停下来想想：如果没有 MVCC，一个快照读会被阻塞多久？高并发下这会导致什么问题？
> ```

#### 适用范围

只在**核心推导步骤**处使用，不要每段都加——太多会打断阅读节奏。建议每篇文章不超过 3 个。

## 三、配套内容调整建议

### 3.1 调整 `feynman-template.md` 的定位

现有的 `docs/algorithm/01-methodology/feynman-template.md` 只覆盖了算法刷题场景。建议将其改造为一个跨领域的方法论参考，新增三个版本的模板：

| 模板 | 适用场景 | 核心结构 |
|------|---------|---------|
| 算法题模板（已有） | 每刷一道算法题后的复盘 | 题目 → 解法 → 漏洞分析 → 优化方向 |
| 技术点模板（新增） | 读完一篇八股文后的复述 | 一句话总结 → 讲给初学者 → 预判追问 → 自己的盲点 |
| 系统设计模板（新增） | 做完一道场景题后的复盘 | 需求拆解 → 核心约束 → 架构决策 → 权衡分析 |

每个模板不需要很长，保持在当前 feynman-template.md 的篇幅级别。

### 3.2 算法板块练习题的"复盘引导"

在每篇练习题（如 `binary-tree-practice-i.md`）的末尾，增加"复盘三步"：

> ```markdown
> ## 做完之后试试
>
> 1. **盖住答案重新做一遍**：不看本文的解法提示，你能在 20 分钟内独立写出来吗？
> 2. **用一句话讲清楚**：如果让你给面试官讲这道题的思路，你会怎么说？（不能直接念代码）
> 3. **举一反三**：这道题的思路可以用来解决哪些其他题？（可以回头看看框架章节的对应部分）
> ```

### 3.3 首页学习路径卡片的微改造

当前 `LearningPath.vue` 的三阶段路径已经很好。建议在每个阶段的标题旁加一个小图标，同时在学习路径的底部加一句提醒：

> 💡 建议每学完一个节点，回到该节点对应的文章末尾做一下「复述自测」——确认自己能讲出来才算真正掌握。

## 四、执行优先级

| 优先级 | 内容 | 预计工作量 |
|--------|------|-----------|
| P0 | 为核心文章添加「思考锚点」段落（每篇 3-5 行） | 每篇 10-15 分钟 |
| P0 | 为核心文章添加「复述自测」引导（每篇 3 个问题） | 每篇 10 分钟 |
| P1 | 在长文章中穿插「读者思考」微提示 | 每篇 5 分钟 |
| P1 | 扩展 feynman-template.md 为跨领域版本 | 半天 |
| P2 | 维护跨域关联表（thinking-links.json）并渲染 | 一次性半天 + 持续维护 |
| P2 | 练习题末尾加"复盘三步" | 每篇 5 分钟 |

## 五、写作风格指引

为保证改造后的内容与现有风格统一，请注意以下几点：

1. **保持口语化，不要写"说教文"**。用"你觉得"、"停下来想想"而不是"读者应该"、"学习者必须"。
2. **保持现有 markdown 结构**——锚点段落用 `## 思考锚点` 标题，复述自测用 `## 复述自测` 标题，思考提示用 `> 🤔` 引用块。
3. **思考锚点不超过 5 行**，复述自测不超过 3 个问题。短即是美。
4. **不要追求面面俱到**。每篇文章挑 1-2 个最关键的推导步骤加"读者思考"微提示，其他地方保持原文流畅度。
5. **尊重现有内容的风格**。比如算法板块的文章偏实战风格，思考锚点要贴合"解题思路"的视角；Java 八股文偏原理追问风格，思考锚点要贴合"底层约束"的视角。

## 六、与现有工具的配合

| 现有工具 | 改造后的配合 |
|---------|-------------|
| `ik:mastery`（掌握状态） | 读者完成"复述自测"后，可以更有底气地标记为 mastered；答不上来则自然保持 learning |
| `ik:recent`（最近阅读） | 后续可以扩展为"间隔复习提醒"——读者标记 mastered 后，在 1/3/7 天后重新推送该文章的复述自测 |
| `ProblemLinker.vue`（题目链接） | 跨域关联（改造 C）是在 ProblemLinker 之上的深层连接，连接的是"思维模式"而非单纯的题目 |
| `ContinueReading.vue`（继续学习） | 在"继续学习"卡片的掌握状态旁，可以加一个小图标提示"该做复述自测了" |
| `LearningPath.vue`（学习路径） | 路径底部加复述引导，节点的掌握状态可以与复述自测的完成情况联动 |
