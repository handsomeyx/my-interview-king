## 一、整体评估

### 做得好的地方

**Java 板块的文章质量非常扎实**，已经形成了统一的、面向面试的深度内容结构：

| 结构要素 | 说明 | 质量 |
|---------|------|------|
| 思考锚点 | 3-5 行，先讲物理/工程约束再引出技术 | ✅ 到位 |
| Q&A + 追问 + 易错点 | 每道题三层深度，符合面试追问逻辑 | ✅ 到位 |
| 易错点速查表 | 文末一张表格，高频考点一页速览 | ✅ 到位 |
| 读者思考微提示 | 正文中穿插 `🤔 停下来想想` 引用块 | ✅ 到位 |
| 复述自测 | 文末三个引导性问题 | ✅ 到位 |
| 代码示例 | 精简、紧扣核心逻辑 | ✅ 到位 |

`lock.md`、`indexing.md`、`garbage-collection.md`、`persistence-cache-problems.md` 这四篇是标杆，可以作为其他板块的参照标准。

### 存在的差距

把 Java 板块的标杆和算法、AI 板块对比，发现三类差距：

| 差距类型 | 具体表现 | 涉及板块 |
|---------|---------|---------|
| **结构不统一** | AI 板块文章缺少"易错点速查表"和"读者思考微提示"；算法框架文章缺少"追问"环节 | AI、算法框架 |

## 二、算法板块优化建议

### 2.1 算法框架文章需要向 Java 板块的深度对齐

以 `dynamic-programming/index.md` 为例，当前的内容结构是：

```
思考锚点 → 算法原理 → 框架模板 → 适用场景 → 注意事项 → 示例 → 总结 → 复述自测
```

这个结构偏"教材"，缺少面试追问深度。建议改造为：

```
思考锚点 → Q1: 核心思想（最优子结构 + 重叠子问题）→ Q2: 怎么定义状态 → Q3: 怎么找状态转移 → Q4: 有哪些常见变种 → Q5: 怎么识别一道题能用 DP → 易错点速查表 → 读者思考微提示 → 复述自测
```

具体改造要点：

#### a) 去掉"算法原理"和"注意事项"这两个空泛的章节

当前 `dynamic-programming/index.md` 的"算法原理"和"注意事项"偏教科书式的定义，对面试帮助不大。建议把这些内容拆解进 Q&A 中。

**当前写法（偏教材）**：
> 动态规划（Dynamic Programming，DP）是一种用于解决具有重叠子问题和最优子结构的问题的算法方法。

**建议改为（偏面试追问）**：
> Q1: 动态规划的核心是什么？
> **答**：两个特征——最优子结构（大问题的最优解包含子问题的最优解）和重叠子问题（子问题会被重复计算）。如果一道题满足这两个特征，DP 大概率能解。
>
> **追问**：怎么判断一道题有"最优子结构"？→ 假设你已经知道了子问题的最优解，能不能用它直接构造出大问题的最优解？如果能，就是最优子结构。如果不能（比如"最长上升子序列"中，知道了前 i 个元素的 LIS 长度，不一定能推出前 i+1 个的），需要重新定义状态。

#### b) 增加"追问"环节

每道核心 Q&A 后面加 1-2 个追问。比如在讲完 DP 状态定义后：

> **追问**：为什么有些 DP 题必须用二维数组？→ 因为状态需要两个维度才能完整描述（如 `dp[i][j]` 表示"前 i 个物品、容量 j 时的最大价值"）。如果只用一维，状态信息就丢了。但一维 DP 不是"简化版二维 DP"——有些问题天生就是一维状态（如最大子数组和），硬写成二维反而绕远。

#### c) 增加"读者思考"微提示

在状态转移方程讲解处加：

> 🤔 停下来想想：`dp[i] = max(dp[i-1] + nums[i], nums[i])` 这个转移方程的本质是什么？它在做什么决策？

#### d) 增加"易错点速查表"

在文末加一张表：

| 知识点 | 关键 |
|-------|------|
| 最优子结构 | 大问题最优解包含子问题最优解；用"假设子问题已知，能否构造大问题"验证 |
| 状态定义 | 错了全白搭；从"需要哪些信息才能做决策"反推 |
| 状态转移 | 每个状态有哪些选择，每种选择把你带到哪个新状态 |
| 一维 vs 二维 | 不是"简化关系"，是"状态维度不同" |
| 空间优化 | 滚动数组只依赖前一行/前一列，才能压空间 |

### 2.2 练习题文章需要加"复盘三步"

以 `sliding-window-practice.md` 为例，当前已经有了"框架速记 + 10 道题目 + 精讲 3 道"的结构，非常扎实。但缺少做完后的复盘引导。建议在文章末尾追加：

```markdown
## 做完之后试试

1. **盖住答案重新做一遍**：不看本文的解法提示，你能在 20 分钟内独立写出来吗？
2. **用一句话讲清楚**：如果让你给面试官讲这道题的思路，你会怎么说？（不能直接念代码）
3. **举一反三**：这道题的"收缩条件"和"结果更新位置"是怎么和其他题不同的？把 10 道题的差异点列出来。
```

### 2.3 算法框架文章之间的交叉引用

当前各框架文章（DP、滑动窗口、二分、DFS/BFS）各自独立。建议在每篇框架文章的"复述自测"之后加一行：

> 你可能还想看看：[二分搜索框架](../00-algorithm-frameworks/binary-search/)（同样是"缩小范围"思想的另一类应用）

## 三、AI 板块优化建议

AI 板块的文章存在**两个核心问题**：

1. **内容可信度存疑**——部分技术描述有偏差
2. **风格与 Java 板块严重脱节**——读起来像两篇不同的文章

### 3.1 技术准确性修正

以下是审读中发现的具体技术偏差，建议修正：

#### a) `ai/03-mcp/index.md` 的 MCP 架构描述

当前写法：
> 架构包含以下核心组件：消息中枢（kafka 做命令总线）、控制单元、状态反馈器

**问题**：MCP 的标准通信机制是 stdio（本地进程通信）和 SSE（Server-Sent Events，远程网络通信），不是 Kafka。把 Kafka 作为 MCP 的消息中枢是对 MCP 协议的误解。MCP 的设计哲学是轻量级、低延迟，用的是 JSON-RPC 风格的请求-响应模式，不需要重型 MQ。

**建议修改**：把 Kafka 相关的描述去掉，改为：
> MCP 的标准通信机制有两种：
> - **stdio 模式**（本地开发/调试）：MCP Server 作为本地子进程，通过标准输入输出与 Agent 通信，零网络开销
> - **SSE 模式**（远程部署）：MCP Server 作为独立服务，通过 HTTP SSE 长连接与 Agent 通信，支持跨机器部署

#### b) MCP 与 RESTful API 的区别描述

当前写法：
> RESTful API 是面向后端服务的，标准格式是请求-响应，无状态

**问题**：RESTful API 不一定无状态（可以用 Session/Cookie/Token 维持状态），且 RESTful 也支持多轮交互。MCP 和 RESTful 的核心区别不是"有没有状态"，而是：
- MCP 是**面向 LLM 的协议**——它在协议层面定义了工具发现（tools/list）、工具调用（tools/call）、资源访问（resources/read）等原语，LLM 可以自主发现和调用
- RESTful 是**面向客户端的协议**——需要开发者手动定义接口文档，LLM 很难直接理解和调用

**建议修改**为更准确的表述。

#### c) `ai/02-agent/index.md` 的部分描述

当前写法整体不错，但在"主流 Agent 架构"部分，缺少对各架构之间**演进关系**的说明。建议加一句：

> 这些架构不是孤立的，而是在不同复杂度下的选择：Plan-and-Execute 适合确定性任务，Reflexion 适合需要纠错的任务，TOT/GOT 适合复杂推理任务。实际工程中常混合使用。

### 3.2 结构对齐：向 Java 板块看齐

AI 板块的文章（特别是 `ai/03-mcp/index.md`）在结构上与 Java 板块差距最大。具体缺失：

| 结构要素 | Java 板块 | AI 板块现状 | 建议 |
|---------|----------|------------|------|
| 思考锚点 | ✅ 有 | Agent 有，MCP 没有 | 为 MCP 加锚点 |
| Q&A 结构 | ✅ 统一 | MCP 是叙述体 | 改为 Q&A |
| 追问环节 | ✅ 每道题有 | 无 | 加追问 |

#### MCP 文章改造示例

当前 MCP 文章的结构是"大段叙述"，建议改造为 Q&A：

```markdown
# MCP：让 Agent 和工具对话的协议

## 思考锚点

LLM 很强，但不能直接访问你的文件、数据库、或其他 AI 服务。要让 LLM 真正帮你干活，必须有一套标准化的"对话协议"——告诉 LLM 有哪些工具可以用、怎么用、用完怎么把结果返回。

MCP 就是这样一套协议。它定义了 Agent 和工具之间的"对话格式"，让 Agent 能自动发现可用工具、调用工具、获取结果。

本文要讲清楚 MCP 的核心概念、通信机制、开发模式和安全实践。

---

## Q1：MCP 到底解决了什么问题？

**答**：三个核心问题：
1. **工具发现**：Agent 怎么知道有哪些工具可以用？→ MCP 定义了 `tools/list` 接口，Agent 可以主动查询
2. **工具调用**：Agent 怎么正确调用一个工具？→ MCP 定义了 `tools/call` 接口，传入工具名和结构化参数
3. **结果返回**：工具怎么把结果返回给 Agent？→ MCP 统一了结果格式（content + metadata），Agent 可以直接消费

**追问**：为什么不让 LLM 直接调 HTTP API？→ 因为 LLM 需要"知道"有哪些 API、每个 API 的参数和返回格式，这通常需要手动写 prompt。MCP 把这些信息做成了协议原语，Agent 可以自动发现和调用，不需要硬编码。

**易错点**：MCP 不是"新的编程语言"，它是**协议**——和 HTTP、TCP 类似，定义的是通信规则，不是实现语言。

## Q2：MCP 的通信模式有哪些？
```

## 六、总结

当前项目的内容基础非常扎实——Java 板块已经达到了面试知识库的标杆水平。下一步的核心任务是**把 Java 板块的标杆结构复制到算法和 AI 板块**，并修正 AI 板块中存在的技术偏差。

改完之后，整个站点会呈现：

- **统一的学习体验**：无论读哪个板块的文章，都是"锚点→追问→速查→自测"的闭环
- **统一的深度标准**：每篇文章都有追问、易错点、读者思考，不会出现"有的文章深有的文章浅"
- **统一的技术准确性**：修正 AI 板块的偏差后，全站内容的技术可信度一致
